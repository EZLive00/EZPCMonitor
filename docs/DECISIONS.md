# 决策记录（ADR）

> 这里记的是**已经拍板的结论和理由**，不是待办清单。改动架构前先读一遍，避免重复讨论。
> 每条决策都写清楚「为什么」，因为半年后最容易被忘掉的正是理由——只留结论的话，
> 后人会以为这是随手定的，然后随手改掉。

格式：编号 · 日期 · 状态（生效 / 已被取代）

## ADR-001 产品定位：从「监控器」扩为「PC 工具箱」

**日期**：2026-10-22 · **状态**：生效

**背景**：最初定位是「轻量级硬件监控 + 悬浮窗」。实际使用中，用户对磁盘健康、测速这类
「平时要单独装个小工具」的需求，和看 CPU 温度是同一类需求。

**决定**：定位改为 **PC 常用基础工具集**——监控是第一个模块，磁盘检测是第二个，后续同类
小工具（电池健康、网络诊断等）按同一套交互收进来。核心约束不变：**轻量、零遥测、不开内核驱动**。

**影响**：
- 导航从「一个主面板」变成「主面板 + 各模块的二级页面」
- 每加一个工具都要回答两个问题：它值得占用常驻内存吗？它需要提权吗？
- 不能因为功能变多就把启动时间和包体撑起来——这是和「装一堆小工具」竞争的唯一理由

## ADR-002 平台差异策略：能做满就做满，做不了如实标注

**日期**：2026-10-22 · **状态**：生效

**背景**：部分能力天然平台不均（Windows 能读 Flash ID、macOS 不能；macOS 温度免 root、
Windows 要管理员）。

**决定**：
1. **不在弱平台上砍掉强平台的功能**。Windows 能做到的，Windows 版就做满。
2. 弱平台在**同一位置**显示「此平台不支持」+ 一句原因，而不是隐藏该功能。
3. 不允许为了「三端看起来一样」而降低任何一端的能力。

**理由**：用户要的是「不用再装别的工具」。假装功能不存在，用户会以为是我们没做；
明确说明平台限制，用户知道该去哪儿找。

## ADR-003 磁盘健康：三层数据 + 措辞不得过度承诺

**日期**：2026-10-22 · **状态**：生效

**背景**：`percentage_used`（已用寿命）经常被当成「还能用多久」，但它是**磨损记账**，
不是故障预测。Backblaze 的统计显示相当比例的健康盘在失效前 SMART 完全正常；反过来
`SMART Status: Verified` 只意味着「没有属性越过阈值」，是一个极低的标准。

**决定**：
1. 数据分三层：`diskutil`（系统级状态）→ `smartctl`（完整 SMART）→ 拿不到就降级并说明原因。
2. **措辞**：不叫「健康良好」，叫「SMART 正常（未触发阈值）」；不叫「剩余寿命」，叫「磨损」。
3. 结论只分三档：正常 / 需留意 / 已告警。
4. 排序原则：**已发生的异常（介质错误、备用块、严重警告位）优先于磨损百分比**。
5. 页面上必须有一句：磨损是厂商标称耐久度的估算，不代表故障预测。

**影响**：任何新增的磁盘指标都要先回答「它是测量值、估算值，还是推测值」，推测值不上线。

## ADR-004 不显示推断出来的字段

**日期**：2026-10-22 · **状态**：生效

**背景**：用户想知道 SSD 的 NAND 类型（TLC / QLC）。结论是**读不到**：
- SMART / NVMe 标准日志里没有这个字段，三平台都没有
- 只有厂商私有的 Flash ID 命令能读，且仅部分主控支持；Apple 自研主控不开放
- 型号查表不可靠（同型号不同批次换颗粒）

**决定**：不做「颗粒类型」字段。同理适用于任何只能靠推测得出的指标。

**理由**：一个工具箱里最贵的资产是「显示出来的数字可信」。宁可少一个字段。

**注**：Windows 版可以作为**实验性深度检测**单独提供（默认关闭、需管理员、标注仅支持部分主控），
但不得混进磁盘健康页，也不得作为默认展示。

## ADR-005 smartctl 依赖策略：自带 → 原生 → 兜底

**日期**：2026-10-22 · **状态**：生效（分阶段执行）

**背景**：macOS 上不装 `smartmontools`，磁盘页只能拿到容量、实时读写、`SMART Status`、
固态/机械——**80% 的价值缺失**。要求用户 `brew install` 与「工具箱」定位直接冲突。

**决定**：三阶段，前一步不阻塞后一步。

| 阶段 | 做法 | 状态 |
|---|---|---|
| 1 | **随包自带** `smartctl` 二进制，优先使用；系统已装的作为备选 | ✅ 已完成（2026-10-22） |
| 2 | 按平台写**原生读取**，替换掉子进程调用 | 待办 |
| 3 | 原生可用的平台上，自带 `smartctl` 退化为**兜底**（外置盘、老设备） | 待办 |

**阶段 1 的具体事实（已核实）**：
- `smartctl` 单文件 **705 KB**（arm64），`otool -L` 只链 CoreFoundation / IOKit / libc++，
  **没有 Homebrew dylib 依赖**，可直接放进 `Contents/Resources/bin/`
- 通用二进制约 1.4 MB，App 从 3.4 MB → 约 4.8 MB，可接受
- 许可证 **GPL-2.0**：通过 `fork/exec` 调用属于「同一介质上的独立程序」（mere aggregation），
  不传染本项目的代码；但必须随包附 LICENSE 并提供源码获取方式，且不得修改该二进制
- macOS 公证要求嵌套的每个 Mach-O 用同一 Team ID 签名并带 hardened runtime；
  **待验证**：hardened runtime 下能否打开 IOKit 的 NVMe 用户客户端
- 自带二进制要在运行时做一次可用性校验（架构不匹配时静默回落到系统版本）

**阶段 2 的技术路径（已确认可行）**：

| 平台 | NVMe 健康日志（log page 0x02） | ATA 属性表 |
|---|---|---|
| macOS | IOKit `IONVMeSMARTInterface` 用户客户端，**无需 root** | 同一套接口 |
| Windows | `DeviceIoControl` + `IOCTL_STORAGE_PROTOCOL_COMMAND`（ProtocolTypeNvme） | `SMART_RCV_DRIVE_DATA` |
| Linux | `/dev/nvme0` + `NVME_IOCTL_ADMIN_CMD` | `SG_IO` / `HDIO_DRIVE_CMD` |

**阶段 1 落地时踩的坑（留给后来人）**：
1. `bundle.resources` 用**对象映射**（`{"src": "dst"}`）形式时，本机 `tauri build` 会报
   `Permission denied (os error 13)`，换成**数组**形式就好了。用数组时相对路径会被保留，
   所以资源放在 `src-tauri/resources/bin/smartctl`，运行时路径是
   `<resource_dir>/resources/bin/smartctl`（多一层 `resources/` 不是笔误）。
2. 源文件必须是**可执行**的（755），Tauri 复制时保留权限；644 会让打进包里的二进制无法执行。
3. 运行时要做一次 `--version` 探测再决定用不用自带的：arm64 单架构二进制在 Intel Mac 上
   会 exec 失败，必须静默回落到系统版本，不能让整个磁盘页报错。探测结果缓存在 `OnceLock` 里。
4. 验证方法：临时把系统的 `/opt/homebrew/bin/smartctl` 改名，如果磁盘页仍然有数据，
   说明用的确实是自带的那个（本机已这样验证过）。

**为什么先自带再原生**：自带能立刻让三端体验一致，原生是纯收益替换（去掉 GPL 牵绊、
去掉 fork、去掉外部文件）。反过来先写原生，会在三个平台上各卡一次，交付周期长得多。

## ADR-006 磁盘详情用应用内弹窗，不用独立窗口

**日期**：2026-10-22 · **状态**：生效

**背景**：详情页（属性表 + 实时曲线 + 测速）信息量大，塞进首页会淹没主要指标。

**决定**：一级页面（首页 DISK 卡）只放：盘名、挂载点、容量条、实时读写、状态点、「详情」入口。
其余全部进**应用内弹窗**。

**理由**：独立窗口要多一个 WebView，常驻约 +50 MB；与轻量目标冲突。
代价是不能拖到第二块屏，暂时接受。

## ADR-007 测速只做顺序读写

**日期**：2026-10-22 · **状态**：生效

**背景**：CrystalDiskMark 做 4K 随机、队列深度矩阵，一次完整跑分几分钟。

**决定**：只做顺序写 + 顺序读各一次（默认 512 MB），给两个 MB/s 数字。

**理由**：这两个数字足够回答「这块盘是不是掉速了 / 是不是 QLC 掉速」。随机性能是评测机构的需求，
不是日常监控的需求。写盘量也要克制——SSD 的寿命是有限的，不能为了跑分替用户消耗它。

**实现要点**：写完必须 `fsync`，读时绕 page cache（macOS `F_NOCACHE` / Linux `fadvise DONTNEED`），
否则测出来是内存速度。测速文件用后即删，并在结果里显示实际路径。

## ADR-008 复杂信息进二级页面，一级只留「一眼」

**日期**：2026-10-22 · **状态**：生效

**背景**：磁盘健康最初把完整属性表直接展开在首页磁盘卡里，十几行属性把主要指标（容量、
实时读写）挤到看不见的位置。

**决定**：每个工具模块都按「一级概览 + 二级详情」组织：
- 一级：只放**不需要解释**的数字和一个状态点
- 二级：应用内弹窗，放属性表、曲线、操作（测速等）

**理由**：首页是"扫一眼"的场景，不是"研究"的场景。把研究用的数据放在扫一眼的页面上，
两种场景互相破坏。后续接入的其它工具（电池、网络诊断）沿用同一套结构。

## ADR-009 主面板与悬浮窗互斥

**日期**：2026-10-22 · **状态**：生效

**背景**：主面板打开时悬浮窗仍然挂在桌面上，既挡视线，又让同一份指标被两个 WebView 各渲染一遍。

**决定**：
1. 打开主面板时自动 `hide()` 悬浮窗，并记一个标记「是我们收起来的」。
2. 主面板关闭（销毁窗口）后，**只有标记为真时**才把悬浮窗放回来。
3. 用户从托盘手动显示/隐藏过悬浮窗，就清除这个标记——之后关面板不再自作主张。

**理由**：互斥是默认体验，但不能覆盖用户的显式操作。判断依据必须是「谁隐藏的」，
而不是「现在是否可见」，否则用户手动关掉的悬浮窗会被关面板的动作莫名其妙地弹回来。

## ADR-010 采集频率：三档预设 + 自定义，改完当拍生效

**日期**：2026-10-22 · **状态**：生效

**背景**：采集节奏原本硬编码为 1s。1s 对"看曲线"很合适，但让程序一直以 1s 频率唤醒
CPU/网络/磁盘采样，在笔记本上是要耗电的；而只看温度、容量的用户根本不需要这个精度。
另一方面，把频率写死会让「省电」和「灵敏」二选一。

**决定**：
1. 托盘菜单加 `监控频率` 子菜单：**高（1 秒）/ 中（5 秒）/ 低（10 秒）** 三个预设，
   外加 `自定义…`。子菜单标题直接显示当前值（`监控频率 · 5 秒`），
   因为自定义档位（比如 2.5s）不在三个预设里，三个都不打勾，只有标题能说清现在是几秒。
2. 主面板右上角齿轮 → 弹出面板，同样三档 + 一个秒数输入框，范围 **0.5–60 秒**。
   两端都会夹：前端做即时校验，后端 `clamp` 兜底，**以后端返回值为准**。
3. 间隔存在 `settings.json`（系统应用配置目录），启动时先读再起采集线程，
   否则第一拍会用默认值把用户改过的 5s 冲掉。
4. 采集线程每拍**现读**一次间隔，不等当前 sleep 结束；sleep 切成 ≤250ms 的小片，
   每片检查一次间隔是否变化，变了立刻按新节奏走。

**理由**：
- 预设是给"不想想"的场景，自定义是给"知道自己要什么"的场景，两者不冲突，
  同一个 popover 里放得下，就没必要二选一。
- 频率是**全局状态**而不是前端状态：托盘和主面板都能改，真值必须放在 Rust 侧
  （`AppState.interval_ms`），前端只是镜像，靠 `settings:interval` 事件同步。
  否则两个入口各改各的，界面上会出现"两个当前值"。
- 不能按时长做历史缓冲：`HISTORY_CAP` 按**点数**（300）截断而不是按时长，
  改频率不需要重算容量；代价是 10s 一档时缓冲覆盖 50 分钟而不是 5 分钟，这对用户是好事。

**已知取舍**：频率拉长后，一级页面的曲线时间跨度会跟着变（120 点 × 间隔），
界面上没有标时间轴，只有设置面板里一句提示。要标时间轴的话得给 sparkline 加时间刻度，
属于另一个量级的改动，暂时不做。

## ADR-011 历史记录：默认关闭、固定 10 秒采样、JSONL 追加写

**日期**：2026-10-23 · **状态**：生效

**背景**：需要「状态可回溯」——出问题时能回头看「半小时前那波卡顿到底是谁吃的 CPU」。
但监控程序长期驻留，写盘策略一旦选错，要么把用户硬盘写满，要么把数据写得太粗看不出问题。

**决定**：
1. **默认关闭**。开启后每 10 秒记一条，用户自己选保留时长（1 小时 / 6 小时 / 24 小时 /
   7 天 / 30 天，或自定义 10 分钟–90 天）。
2. **采样节奏与采集频率解耦**：界面刷新可以是 1 秒，落盘固定 10 秒一条。
3. 存储是 **JSON Lines**（一行一条），只追加；修剪时把保留窗口内的行搬到临时文件再
   `rename` 覆盖。
4. 每条记录键名压到一个字母（`t/c/m/p/r/w/d/g`），一条约 85 字节。
5. 「预计占用」用**实测的每条字节数**（`bytes / count`）反算，不在前后端各写一个魔法常量。

**理由**：
- 默认关闭是底线：这个程序原本的卖点是「零网络零落盘」，悄悄开始写文件不能算特性。
  开启入口在设置弹窗里，旁边就是各档位的预估占用，用户是看着数字点头的。
- 10 秒一条的理由：回溯看的是趋势。1 秒粒度会让文件大十倍（30 天 200 MB），
  而 10 秒粒度下 30 天约 21 MB，且仍能看清「哪十分钟在飙」。
- `rename` 是原子的：修剪时先写 `history.jsonl.tmp` 再覆盖，掉电最坏是丢掉本次修剪，
  不会留下半截文件。
- 一行一条而不是一个 JSON 数组：追加是 O(1)，崩溃时最多丢最后一行；数组格式每次写都得
  重写整个文件。

**已知取舍**：
- 修剪是整文件重写（约几十 ms），所以只在文件超过预估上限 1.3 倍时才做，
  而不是每次追加都检查。
- 没有做降采样归档：超过保留期的数据直接删，不留「1 小时粒度的一年数据」。
  真要做的话是另一个量级的设计（多级保留 + 后台合并）。

## ADR-012 设置入口：弹窗而非独立页面，齿轮与托盘共用

**日期**：2026-10-23 · **状态**：生效

**背景**：采集频率原本是右上角的一个小浮层，加进历史记录（开关 + 保留时长 + 占用 + 清空）
之后，浮层放不下了；而托盘里也需要一个「设置」入口。

**决定**：
1. 设置改成**应用内弹窗**，按功能分组（监控 / 历史记录 / 关于），复用磁盘详情的
   `.modal-*` 样式。
2. 右上角齿轮、托盘「设置…」、托盘频率子菜单的「更多设置…」三个入口，
   都打开同一个弹窗。
3. 所有改动走 `update_settings(patch)` 一个命令：夹取、落盘、广播 `settings:changed`
   都在后端做一次。

**理由**：设置项会继续变多（开机自启、主题、语言、告警阈值），浮层迟早要重写；
不如在只有三项的时候换成弹窗，布局和交互定下来，后面只是往里加分组。
单个命令 + 单个事件则保证了「托盘改的和弹窗显示的永远是同一个值」。

## ADR-013 多语言：手写字典 + 编译期对齐，Rust 与前端各持一份

**日期**：2026-10-23 · **状态**：生效

**背景**：要支持简体中文、繁體中文、English、日本語、한국어、Français、Español 七种界面语言，
默认跟随系统，设置里可随时切换。界面文案分散在两处：React 组件里的一百多条，
以及**原生侧**（托盘菜单、窗口标题）——后者由系统绘制，拿不到 WebView 里的翻译。

**决定**：
1. **不引 i18n 库**。只需要「查表 + `{var}` 插值 + 单复数」三件事，
   i18next 的命名空间/后端加载/插件体系对一个桌面小工具是纯负担。
   自建 `src/i18n/`：`zh-CN.ts` 是**唯一基准**，`Dict` 类型从它推导，
   另外六份标注 `const strings: Dict`——少一条、多一条、拼错一条键都是**编译错误**，
   不需要人工比对，也不会等到某个界面才看见空白。
2. 语言存 `settings.language`，取值 `auto` 或七个标签之一。**真值在 Rust**，
   前端只是镜像（与 ADR-012 同一套模式）：`get_locale` 给系统语言，
   `settings:changed` 推动切换。系统语言用 `sys-locale`（macOS 走 CFLocale，
   Windows 走 GetUserDefaultLocaleName，Linux 读 LC_ALL/LANG），
   另留 `EZPCM_LANG` 环境变量用于截图和回归测试。
3. 前端状态用**模块级 store + `useSyncExternalStore`**，不用 React Context。
   主面板和悬浮窗是两个独立的 React root，Context 得从根上穿一遍；
   `useI18n()` 在任意位置直接调用即可，非组件代码用 `i18n()` 取当前值。
4. 原生文案（托盘 17 条 + 窗口标题）放在 `src-tauri/src/i18n.rs` 的七张表里，
   并有单元测试保证七种语言覆盖所有键。改语言时 `update_settings` 顺手重建托盘、
   重设窗口标题。
5. **SMART 属性表只做中文/英文两种**。`Percentage Used`、`Available Spare` 这类属性名
   在 smartctl、CrystalDiskInfo 里本来就是英文，硬翻成六种语言既对不上号，
   也容易把「备用块」这类术语译错；界面文案另说，那部分在前端字典里。
   语言一变要 `diskhealth::clear_cache()`——缓存里存的是**已经格式化好的字符串**。
6. 数字、日期、复数走 `Intl`：`Intl.NumberFormat` 处理千分位和小数逗号（法语 `2,5 s`），
   `Intl.DateTimeFormat` + `h23` 出 `14:05`，复数用 `[单数, 复数]` 二元组
   （中日韩两条写一样的，调用方不用关心语言）。
7. 卡片标题（内存/温度/磁盘/网络/进程榜）**参与翻译**：它们是界面文案不是术语，
   韩语用户看到「MEMORY」只会觉得没翻完。CPU/GPU 保持拉丁字母。

**理由**：
- 编译期对齐比任何人工 review 都可靠：漏翻在 CI 就红，而不是等用户截图来报。
- 语言解析只在一处（Rust）做，避免前端 `navigator.language` 和后端各算一次算出不同答案。
- 托盘是系统绘制的，注定要有第二份文案；与其让前端把字符串推过去，不如两边各自持有，
  共用同一套语言标签。

**已知取舍**：
- 两份字典（前端 + 原生），加一条托盘文案要改 Rust，加一条界面文案要改前端。
  界限是「谁能渲染它」，不是「它属于哪个功能」，所以不会重叠。
- 非中文语言的 SMART 属性名是英文，属于有意为之的行业惯例，不是漏翻。
- 数据单位（KB/MB/GB）不本地化（法语理论上写 Ko/Mo/Go），
  统一按 SI 记号显示——跨语言截图对比时反而更清楚。

## ADR-014 主题：一套叠加层变量 + 两处覆盖，首帧不闪

**日期**：2026-10-23 · **状态**：生效

**背景**：深色样式已经定稿且用户认可，现在要加浅色。难点不在「配一套浅色」，
而在**不要写第二套 CSS**——整套界面有五十多处 `rgba(255,255,255,α)` 的半透明面板、
描边、分隔线，如果浅色靠复制一份样式表来实现，以后每改一个间距都要改两遍，
两边迟早会漂移。

**决定**：
1. **叠加层变量**。深色下那些白色半透明全部改成 `rgba(var(--ovl), α)`：
   深色主题 `--ovl: 255,255,255`（提亮），浅色主题 `--ovl: 16,24,40`（压暗）。
   同一个 α 在两种主题下都成立，因为叠加方向反了过来。
   文字同理：`--text-rgb` 给「半透明文字色」，`--dim-rgb` / `--accent-rgb` 备用。
2. **面板本身单独给变量**：`--page` / `--card-bg` / `--card-shadow` / `--modal-bg` /
   `--popover-bg` / `--widget-bg` / `--scrim` / `--shadow` / `--shadow-sm`。
   深色下 `--card-shadow: none`（靠 1px 描边分层），浅色下卡片是白底，
   必须靠一层很淡的投影才有厚度——这是两种主题唯一「结构不同」的地方。
3. **图表色单独一套 `--c-*`**：1.6px 的曲线在深色底上是亮的，在白底上会被冲掉。
   浅色统一压深一档（`#22d3ee → #0891b2`、`#a78bfa → #7c3aed`…），
   磁盘详情页的读写曲线另给 `--c-io-r` / `--c-io-w`，保持深色下的观感一字不变。
4. 主题值 `settings.theme`：`auto` / `dark` / `light`，与语言同构（ADR-013）——
   真值在 Rust，前端用 `useSyncExternalStore` 镜像，`auto` 由前端监听
   `prefers-color-scheme` 解析。落地的动作只有一句
   `document.documentElement.dataset.theme = ...`，不往组件里传色值，
   切主题不触发大范围重渲染。
5. **浅色值写两遍**：一次在 `:root[data-theme="light"]`，一次在
   `@media (prefers-color-scheme: light) { :root:not([data-theme="dark"]) }`。
   第二遍纯粹为了**首帧**——`get_settings` 要跨一次 IPC，那之前页面上还没有
   `data-theme`，只靠属性选择器的话浅色系统上会先闪一下深色。
   另把上次解析出的结果缓存在 `localStorage`，模块加载时立刻用上。
6. **原生标题栏也要跟着走**：`app.set_theme(Some(Theme::Light/Dark))`，
   `auto` 时传 `None` 交还系统。CSS 只管 WebView，标题栏是 macOS 画的，
   不告诉它就会出现「浅色界面顶一条深色标题栏」。
7. 浅色下悬浮窗的不透明度提高一档（`.82/.91` 对 `.74/.82`）：白底叠白字，
   透明度高了字就飘；深色底本身就压得住。

**理由**：
- 一份样式、两组变量，改布局只改一处，两个主题不会各走各的。
- 变量命名按**角色**（`--card-bg`、`--scrim`）而不是按颜色（`--white-4`），
  浅色不是「另一套颜色」而是「同一批角色换一身衣服」。
- 首帧那两遍是唯一可接受的重复，且只重复颜色值，不重复结构。

**已知取舍**：
- 浅色主题的颜色值在 CSS 里出现两次，改色要两边一起改（已注释说明）。
  用构建期变量或 CSS 嵌套能消掉，但不值得为此引入工具链。
- 托盘菜单是系统绘制的，主题跟随 `NSApp.appearance`（`set_theme` 会一并影响），
  不受页面内 `data-theme` 控制——这是对的，系统菜单就该跟系统。
- `auto` 时前端依赖 `prefers-color-scheme`。强制过主题后这个媒体查询反映的是
  **强制值**而不是系统值，所以切回 `auto` 时要先把原生主题复位（`None`），
  前端再跟着 `change` 事件重绘一次。

## ADR-015 程序榜：落盘原始样本，统计全部现算

**日期**：2026-10-23 · **状态**：生效

**背景**：历史记录只存整机指标，能回答「什么时候卡的」，回答不了「是谁卡的」。
需要 top10 高占用程序、按多个维度排序，并要一张能直接发出去的报告图。

讨论中有两个关键分歧，最后都按下面的结论定了。

**决定**：

1. **存原始样本，不存统计结果**。每 30 秒一拍，写进 `procs/` 下按小时分片的 JSONL。
2. **统计全部现算**：平均、峰值、活跃占比、增长都由 `proc_leaders` 从原始样本算。
3. **不要中位数**，换成两列更有信息量的：CPU/磁盘看**活跃占比**，内存看**增长**。
4. **按进程名合并**，且扫全量进程表。
5. GPU 与网络维度在 UI 里**可见但禁用**。
6. 报告图是 **PNG 长图**，默认落下载目录，另给一个复制按钮；时间范围跟随弹窗当前选择。
7. 默认排序用**峰值**。

**理由**：

- 「为什么不存统计」——统计是原始样本的函数，存了统计就等于把「以后还能问什么」
  提前锁死。今天想按峰值排，明天想按「连续高占用时长」排，存了平均/峰值就再也
  算不出来。原始样本一天不到 2 MB，这个代价买回的是可重算性。
- 「中位数为什么没用」——桌面进程的 CPU 是大量 0 组成的稀疏分布：一个每 30 秒里
  只忙 3 秒的程序，中位数恒为 0，和完全不动的进程在表里长得一模一样。
  中位数在这种分布上不描述任何东西。活跃占比直接回答「它是不是一直在动」，
  内存的增长回答「它是不是在漏」，这两个才是用户真正想知道的。
- 「为什么按名字合并、为什么扫全量表」——Chrome 一个应用开二十个进程。
  不合并，榜上全是它的子进程，等于没排；只扫「当前前 20」再合并，会把
  「每个子进程都不高、加起来最高」的应用整个漏掉。
- 「为什么默认按峰值」——平均值会被大量空闲时间稀释，用户点开榜单的第一诉求
  是「谁把我的机器吃满过」。

**已知取舍**：

- 30 秒一拍会漏掉短于 30 秒的尖峰；采样再密，写入和体积都要翻倍，不划算。
- 按名字合并会把「同名但不同程序」混在一起（罕见，且合并后仍能看出是谁）。
- 逐进程 GPU / 网络拿不到，维度置灰而不是显示 0（ADR-002 / ADR-004）。
- 报告图在前端画，颜色要先把 CSS 变量解析成字面量；好处是不用把渲染逻辑
  搬进 Rust，主题换了报告也跟着换。
- 平均的分母是窗口内全部样本数（没出现记 0），所以同一个程序在 1 小时窗和
  24 小时窗里的「平均」不可直接比较——这是有意的，它衡量的是「这段窗口里
  它平均占了多少」。
