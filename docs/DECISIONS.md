# 决策记录（ADR）

> 这里记的是**已经拍板的结论和理由**，不是待办清单。改动架构前先读一遍，避免重复讨论。
> 每条决策都写清楚「为什么」，因为半年后最容易被忘掉的正是理由——只留结论的话，
> 后人会以为这是随手定的，然后随手改掉。

> **ADR-001 ~ ADR-018 记录的是 v0.1（Tauri 2 + React + WebView）时期的决定。**
> v0.2 把外壳换成 AppKit / SwiftUI 之后，其中关于**产品**的判断（定位、措辞、
> 采集口径、历史保留策略）全部继续生效；关于**前端实现**的判断（i18n 放 `src/i18n`、
> 主题用 CSS 变量、报告图走 SVG→canvas）已被原生实现取代。
> 原生的新增决定见文末 ADR-019 起。

格式：编号 · 日期 · 状态（生效 / 已被取代）

## ADR-001 产品定位：从「监控器」扩为「PC 工具箱」

**日期**：2026-10-22 · **状态**：生效

**背景**：最初定位是「轻量级硬件监控 + 悬浮窗」。实际使用中，用户对磁盘健康、测速这类
「平时要单独装个小工具」的需求，和看 CPU 温度是同一类需求。

**决定**：定位改为 **PC 常用基础工具集**——监控是第一个模块，磁盘检测是第二个，后续同类
小工具（电池健康、网络诊断等）按同一套交互收进来。核心约束不变：**轻量、零遥测、不开内核驱动**。

**影响**：
- 导航从「一个主面板」变成「主面板 + 各模块的二级页面」
- 每加一个工具都要回答两个问题：它值得占用常驻内存吗？它需要提权吗？
- 不能因为功能变多就把启动时间和包体撑起来——这是和「装一堆小工具」竞争的唯一理由

## ADR-002 平台差异策略：能做满就做满，做不了如实标注

**日期**：2026-10-22 · **状态**：生效

**背景**：部分能力天然平台不均（Windows 能读 Flash ID、macOS 不能；macOS 温度免 root、
Windows 要管理员）。

**决定**：
1. **不在弱平台上砍掉强平台的功能**。Windows 能做到的，Windows 版就做满。
2. 弱平台在**同一位置**显示「此平台不支持」+ 一句原因，而不是隐藏该功能。
3. 不允许为了「三端看起来一样」而降低任何一端的能力。

**理由**：用户要的是「不用再装别的工具」。假装功能不存在，用户会以为是我们没做；
明确说明平台限制，用户知道该去哪儿找。

## ADR-003 磁盘健康：三层数据 + 措辞不得过度承诺

**日期**：2026-10-22 · **状态**：生效

**背景**：`percentage_used`（已用寿命）经常被当成「还能用多久」，但它是**磨损记账**，
不是故障预测。Backblaze 的统计显示相当比例的健康盘在失效前 SMART 完全正常；反过来
`SMART Status: Verified` 只意味着「没有属性越过阈值」，是一个极低的标准。

**决定**：
1. 数据分三层：`diskutil`（系统级状态）→ `smartctl`（完整 SMART）→ 拿不到就降级并说明原因。
2. **措辞**：不叫「健康良好」，叫「SMART 正常（未触发阈值）」；不叫「剩余寿命」，叫「磨损」。
3. 结论只分三档：正常 / 需留意 / 已告警。
4. 排序原则：**已发生的异常（介质错误、备用块、严重警告位）优先于磨损百分比**。
5. 页面上必须有一句：磨损是厂商标称耐久度的估算，不代表故障预测。

**影响**：任何新增的磁盘指标都要先回答「它是测量值、估算值，还是推测值」，推测值不上线。

## ADR-004 不显示推断出来的字段

**日期**：2026-10-22 · **状态**：生效

**背景**：用户想知道 SSD 的 NAND 类型（TLC / QLC）。结论是**读不到**：
- SMART / NVMe 标准日志里没有这个字段，三平台都没有
- 只有厂商私有的 Flash ID 命令能读，且仅部分主控支持；Apple 自研主控不开放
- 型号查表不可靠（同型号不同批次换颗粒）

**决定**：不做「颗粒类型」字段。同理适用于任何只能靠推测得出的指标。

**理由**：一个工具箱里最贵的资产是「显示出来的数字可信」。宁可少一个字段。

**注**：Windows 版可以作为**实验性深度检测**单独提供（默认关闭、需管理员、标注仅支持部分主控），
但不得混进磁盘健康页，也不得作为默认展示。

## ADR-005 smartctl 依赖策略：自带 → 原生 → 兜底

**日期**：2026-10-22 · **状态**：生效（分阶段执行）

**背景**：macOS 上不装 `smartmontools`，磁盘页只能拿到容量、实时读写、`SMART Status`、
固态/机械——**80% 的价值缺失**。要求用户 `brew install` 与「工具箱」定位直接冲突。

**决定**：三阶段，前一步不阻塞后一步。

| 阶段 | 做法 | 状态 |
|---|---|---|
| 1 | **随包自带** `smartctl` 二进制，优先使用；系统已装的作为备选 | ✅ 已完成（2026-10-22） |
| 2 | 按平台写**原生读取**，替换掉子进程调用 | 待办 |
| 3 | 原生可用的平台上，自带 `smartctl` 退化为**兜底**（外置盘、老设备） | 待办 |

**阶段 1 的具体事实（已核实）**：
- `smartctl` 单文件 **705 KB**（arm64），`otool -L` 只链 CoreFoundation / IOKit / libc++，
  **没有 Homebrew dylib 依赖**，可直接放进 `Contents/Resources/bin/`
- 通用二进制约 1.4 MB，App 从 3.4 MB → 约 4.8 MB，可接受
- 许可证 **GPL-2.0**：通过 `fork/exec` 调用属于「同一介质上的独立程序」（mere aggregation），
  不传染本项目的代码；但必须随包附 LICENSE 并提供源码获取方式，且不得修改该二进制
- macOS 公证要求嵌套的每个 Mach-O 用同一 Team ID 签名并带 hardened runtime；
  **待验证**：hardened runtime 下能否打开 IOKit 的 NVMe 用户客户端
- 自带二进制要在运行时做一次可用性校验（架构不匹配时静默回落到系统版本）

**阶段 2 的技术路径（已确认可行）**：

| 平台 | NVMe 健康日志（log page 0x02） | ATA 属性表 |
|---|---|---|
| macOS | IOKit `IONVMeSMARTInterface` 用户客户端，**无需 root** | 同一套接口 |
| Windows | `DeviceIoControl` + `IOCTL_STORAGE_PROTOCOL_COMMAND`（ProtocolTypeNvme） | `SMART_RCV_DRIVE_DATA` |
| Linux | `/dev/nvme0` + `NVME_IOCTL_ADMIN_CMD` | `SG_IO` / `HDIO_DRIVE_CMD` |

**阶段 1 落地时踩的坑（留给后来人）**：
1. `bundle.resources` 用**对象映射**（`{"src": "dst"}`）形式时，本机 `tauri build` 会报
   `Permission denied (os error 13)`，换成**数组**形式就好了。用数组时相对路径会被保留，
   所以资源放在 `src-tauri/resources/bin/smartctl`，运行时路径是
   `<resource_dir>/resources/bin/smartctl`（多一层 `resources/` 不是笔误）。
2. 源文件必须是**可执行**的（755），Tauri 复制时保留权限；644 会让打进包里的二进制无法执行。
3. 运行时要做一次 `--version` 探测再决定用不用自带的：arm64 单架构二进制在 Intel Mac 上
   会 exec 失败，必须静默回落到系统版本，不能让整个磁盘页报错。探测结果缓存在 `OnceLock` 里。
4. 验证方法：临时把系统的 `/opt/homebrew/bin/smartctl` 改名，如果磁盘页仍然有数据，
   说明用的确实是自带的那个（本机已这样验证过）。

**为什么先自带再原生**：自带能立刻让三端体验一致，原生是纯收益替换（去掉 GPL 牵绊、
去掉 fork、去掉外部文件）。反过来先写原生，会在三个平台上各卡一次，交付周期长得多。

## ADR-006 磁盘详情用应用内弹窗，不用独立窗口

**日期**：2026-10-22 · **状态**：生效

**背景**：详情页（属性表 + 实时曲线 + 测速）信息量大，塞进首页会淹没主要指标。

**决定**：一级页面（首页 DISK 卡）只放：盘名、挂载点、容量条、实时读写、状态点、「详情」入口。
其余全部进**应用内弹窗**。

**理由**：独立窗口要多一个 WebView，常驻约 +50 MB；与轻量目标冲突。
代价是不能拖到第二块屏，暂时接受。

## ADR-007 测速只做顺序读写

**日期**：2026-10-22 · **状态**：生效

**背景**：CrystalDiskMark 做 4K 随机、队列深度矩阵，一次完整跑分几分钟。

**决定**：只做顺序写 + 顺序读各一次（默认 512 MB），给两个 MB/s 数字。

**理由**：这两个数字足够回答「这块盘是不是掉速了 / 是不是 QLC 掉速」。随机性能是评测机构的需求，
不是日常监控的需求。写盘量也要克制——SSD 的寿命是有限的，不能为了跑分替用户消耗它。

**实现要点**：写完必须 `fsync`，读时绕 page cache（macOS `F_NOCACHE` / Linux `fadvise DONTNEED`），
否则测出来是内存速度。测速文件用后即删，并在结果里显示实际路径。

## ADR-008 复杂信息进二级页面，一级只留「一眼」

**日期**：2026-10-22 · **状态**：生效

**背景**：磁盘健康最初把完整属性表直接展开在首页磁盘卡里，十几行属性把主要指标（容量、
实时读写）挤到看不见的位置。

**决定**：每个工具模块都按「一级概览 + 二级详情」组织：
- 一级：只放**不需要解释**的数字和一个状态点
- 二级：应用内弹窗，放属性表、曲线、操作（测速等）

**理由**：首页是"扫一眼"的场景，不是"研究"的场景。把研究用的数据放在扫一眼的页面上，
两种场景互相破坏。后续接入的其它工具（电池、网络诊断）沿用同一套结构。

## ADR-009 主面板与悬浮窗互斥

**日期**：2026-10-22 · **状态**：生效

**背景**：主面板打开时悬浮窗仍然挂在桌面上，既挡视线，又让同一份指标被两个 WebView 各渲染一遍。

**决定**：
1. 打开主面板时自动 `hide()` 悬浮窗，并记一个标记「是我们收起来的」。
2. 主面板关闭（销毁窗口）后，**只有标记为真时**才把悬浮窗放回来。
3. 用户从托盘手动显示/隐藏过悬浮窗，就清除这个标记——之后关面板不再自作主张。

**理由**：互斥是默认体验，但不能覆盖用户的显式操作。判断依据必须是「谁隐藏的」，
而不是「现在是否可见」，否则用户手动关掉的悬浮窗会被关面板的动作莫名其妙地弹回来。

## ADR-010 采集频率：三档预设 + 自定义，改完当拍生效

**日期**：2026-10-22 · **状态**：生效

**背景**：采集节奏原本硬编码为 1s。1s 对"看曲线"很合适，但让程序一直以 1s 频率唤醒
CPU/网络/磁盘采样，在笔记本上是要耗电的；而只看温度、容量的用户根本不需要这个精度。
另一方面，把频率写死会让「省电」和「灵敏」二选一。

**决定**：
1. 托盘菜单加 `监控频率` 子菜单：**高（1 秒）/ 中（5 秒）/ 低（10 秒）** 三个预设，
   外加 `自定义…`。子菜单标题直接显示当前值（`监控频率 · 5 秒`），
   因为自定义档位（比如 2.5s）不在三个预设里，三个都不打勾，只有标题能说清现在是几秒。
2. 主面板右上角齿轮 → 弹出面板，同样三档 + 一个秒数输入框，范围 **0.5–60 秒**。
   两端都会夹：前端做即时校验，后端 `clamp` 兜底，**以后端返回值为准**。
3. 间隔存在 `settings.json`（系统应用配置目录），启动时先读再起采集线程，
   否则第一拍会用默认值把用户改过的 5s 冲掉。
4. 采集线程每拍**现读**一次间隔，不等当前 sleep 结束；sleep 切成 ≤250ms 的小片，
   每片检查一次间隔是否变化，变了立刻按新节奏走。

**理由**：
- 预设是给"不想想"的场景，自定义是给"知道自己要什么"的场景，两者不冲突，
  同一个 popover 里放得下，就没必要二选一。
- 频率是**全局状态**而不是前端状态：托盘和主面板都能改，真值必须放在 Rust 侧
  （`AppState.interval_ms`），前端只是镜像，靠 `settings:interval` 事件同步。
  否则两个入口各改各的，界面上会出现"两个当前值"。
- 不能按时长做历史缓冲：`HISTORY_CAP` 按**点数**（300）截断而不是按时长，
  改频率不需要重算容量；代价是 10s 一档时缓冲覆盖 50 分钟而不是 5 分钟，这对用户是好事。

**已知取舍**：频率拉长后，一级页面的曲线时间跨度会跟着变（120 点 × 间隔），
界面上没有标时间轴，只有设置面板里一句提示。要标时间轴的话得给 sparkline 加时间刻度，
属于另一个量级的改动，暂时不做。

## ADR-011 历史记录：默认关闭、固定 10 秒采样、JSONL 追加写

**日期**：2026-10-23 · **状态**：生效

**背景**：需要「状态可回溯」——出问题时能回头看「半小时前那波卡顿到底是谁吃的 CPU」。
但监控程序长期驻留，写盘策略一旦选错，要么把用户硬盘写满，要么把数据写得太粗看不出问题。

**决定**：
1. **默认关闭**。开启后每 10 秒记一条，用户自己选保留时长（1 小时 / 6 小时 / 24 小时 /
   7 天 / 30 天，或自定义 10 分钟–90 天）。
2. **采样节奏与采集频率解耦**：界面刷新可以是 1 秒，落盘固定 10 秒一条。
3. 存储是 **JSON Lines**（一行一条），只追加；修剪时把保留窗口内的行搬到临时文件再
   `rename` 覆盖。
4. 每条记录键名压到一个字母（`t/c/m/p/r/w/d/g`），一条约 85 字节。
5. 「预计占用」用**实测的每条字节数**（`bytes / count`）反算，不在前后端各写一个魔法常量。

**理由**：
- 默认关闭是底线：这个程序原本的卖点是「零网络零落盘」，悄悄开始写文件不能算特性。
  开启入口在设置弹窗里，旁边就是各档位的预估占用，用户是看着数字点头的。
- 10 秒一条的理由：回溯看的是趋势。1 秒粒度会让文件大十倍（30 天 200 MB），
  而 10 秒粒度下 30 天约 21 MB，且仍能看清「哪十分钟在飙」。
- `rename` 是原子的：修剪时先写 `history.jsonl.tmp` 再覆盖，掉电最坏是丢掉本次修剪，
  不会留下半截文件。
- 一行一条而不是一个 JSON 数组：追加是 O(1)，崩溃时最多丢最后一行；数组格式每次写都得
  重写整个文件。

**已知取舍**：
- 修剪是整文件重写（约几十 ms），所以只在文件超过预估上限 1.3 倍时才做，
  而不是每次追加都检查。
- 没有做降采样归档：超过保留期的数据直接删，不留「1 小时粒度的一年数据」。
  真要做的话是另一个量级的设计（多级保留 + 后台合并）。

## ADR-012 设置入口：弹窗而非独立页面，齿轮与托盘共用

**日期**：2026-10-23 · **状态**：生效

**背景**：采集频率原本是右上角的一个小浮层，加进历史记录（开关 + 保留时长 + 占用 + 清空）
之后，浮层放不下了；而托盘里也需要一个「设置」入口。

**决定**：
1. 设置改成**应用内弹窗**，按功能分组（监控 / 历史记录 / 关于），复用磁盘详情的
   `.modal-*` 样式。
2. 右上角齿轮、托盘「设置…」、托盘频率子菜单的「更多设置…」三个入口，
   都打开同一个弹窗。
3. 所有改动走 `update_settings(patch)` 一个命令：夹取、落盘、广播 `settings:changed`
   都在后端做一次。

**理由**：设置项会继续变多（开机自启、主题、语言、告警阈值），浮层迟早要重写；
不如在只有三项的时候换成弹窗，布局和交互定下来，后面只是往里加分组。
单个命令 + 单个事件则保证了「托盘改的和弹窗显示的永远是同一个值」。

## ADR-013 多语言：手写字典 + 编译期对齐，Rust 与前端各持一份

**日期**：2026-10-23 · **状态**：生效

**背景**：要支持简体中文、繁體中文、English、日本語、한국어、Français、Español 七种界面语言，
默认跟随系统，设置里可随时切换。界面文案分散在两处：React 组件里的一百多条，
以及**原生侧**（托盘菜单、窗口标题）——后者由系统绘制，拿不到 WebView 里的翻译。

**决定**：
1. **不引 i18n 库**。只需要「查表 + `{var}` 插值 + 单复数」三件事，
   i18next 的命名空间/后端加载/插件体系对一个桌面小工具是纯负担。
   自建 `src/i18n/`：`zh-CN.ts` 是**唯一基准**，`Dict` 类型从它推导，
   另外六份标注 `const strings: Dict`——少一条、多一条、拼错一条键都是**编译错误**，
   不需要人工比对，也不会等到某个界面才看见空白。
2. 语言存 `settings.language`，取值 `auto` 或七个标签之一。**真值在 Rust**，
   前端只是镜像（与 ADR-012 同一套模式）：`get_locale` 给系统语言，
   `settings:changed` 推动切换。系统语言用 `sys-locale`（macOS 走 CFLocale，
   Windows 走 GetUserDefaultLocaleName，Linux 读 LC_ALL/LANG），
   另留 `EZPCM_LANG` 环境变量用于截图和回归测试。
3. 前端状态用**模块级 store + `useSyncExternalStore`**，不用 React Context。
   主面板和悬浮窗是两个独立的 React root，Context 得从根上穿一遍；
   `useI18n()` 在任意位置直接调用即可，非组件代码用 `i18n()` 取当前值。
4. 原生文案（托盘 17 条 + 窗口标题）放在 `src-tauri/src/i18n.rs` 的七张表里，
   并有单元测试保证七种语言覆盖所有键。改语言时 `update_settings` 顺手重建托盘、
   重设窗口标题。
5. **SMART 属性表只做中文/英文两种**。`Percentage Used`、`Available Spare` 这类属性名
   在 smartctl、CrystalDiskInfo 里本来就是英文，硬翻成六种语言既对不上号，
   也容易把「备用块」这类术语译错；界面文案另说，那部分在前端字典里。
   语言一变要 `diskhealth::clear_cache()`——缓存里存的是**已经格式化好的字符串**。
6. 数字、日期、复数走 `Intl`：`Intl.NumberFormat` 处理千分位和小数逗号（法语 `2,5 s`），
   `Intl.DateTimeFormat` + `h23` 出 `14:05`，复数用 `[单数, 复数]` 二元组
   （中日韩两条写一样的，调用方不用关心语言）。
7. 卡片标题（内存/温度/磁盘/网络/进程榜）**参与翻译**：它们是界面文案不是术语，
   韩语用户看到「MEMORY」只会觉得没翻完。CPU/GPU 保持拉丁字母。

**理由**：
- 编译期对齐比任何人工 review 都可靠：漏翻在 CI 就红，而不是等用户截图来报。
- 语言解析只在一处（Rust）做，避免前端 `navigator.language` 和后端各算一次算出不同答案。
- 托盘是系统绘制的，注定要有第二份文案；与其让前端把字符串推过去，不如两边各自持有，
  共用同一套语言标签。

**已知取舍**：
- 两份字典（前端 + 原生），加一条托盘文案要改 Rust，加一条界面文案要改前端。
  界限是「谁能渲染它」，不是「它属于哪个功能」，所以不会重叠。
- 非中文语言的 SMART 属性名是英文，属于有意为之的行业惯例，不是漏翻。
- 数据单位（KB/MB/GB）不本地化（法语理论上写 Ko/Mo/Go），
  统一按 SI 记号显示——跨语言截图对比时反而更清楚。

## ADR-014 主题：一套叠加层变量 + 两处覆盖，首帧不闪

**日期**：2026-10-23 · **状态**：生效

**背景**：深色样式已经定稿且用户认可，现在要加浅色。难点不在「配一套浅色」，
而在**不要写第二套 CSS**——整套界面有五十多处 `rgba(255,255,255,α)` 的半透明面板、
描边、分隔线，如果浅色靠复制一份样式表来实现，以后每改一个间距都要改两遍，
两边迟早会漂移。

**决定**：
1. **叠加层变量**。深色下那些白色半透明全部改成 `rgba(var(--ovl), α)`：
   深色主题 `--ovl: 255,255,255`（提亮），浅色主题 `--ovl: 16,24,40`（压暗）。
   同一个 α 在两种主题下都成立，因为叠加方向反了过来。
   文字同理：`--text-rgb` 给「半透明文字色」，`--dim-rgb` / `--accent-rgb` 备用。
2. **面板本身单独给变量**：`--page` / `--card-bg` / `--card-shadow` / `--modal-bg` /
   `--popover-bg` / `--widget-bg` / `--scrim` / `--shadow` / `--shadow-sm`。
   深色下 `--card-shadow: none`（靠 1px 描边分层），浅色下卡片是白底，
   必须靠一层很淡的投影才有厚度——这是两种主题唯一「结构不同」的地方。
3. **图表色单独一套 `--c-*`**：1.6px 的曲线在深色底上是亮的，在白底上会被冲掉。
   浅色统一压深一档（`#22d3ee → #0891b2`、`#a78bfa → #7c3aed`…），
   磁盘详情页的读写曲线另给 `--c-io-r` / `--c-io-w`，保持深色下的观感一字不变。
4. 主题值 `settings.theme`：`auto` / `dark` / `light`，与语言同构（ADR-013）——
   真值在 Rust，前端用 `useSyncExternalStore` 镜像，`auto` 由前端监听
   `prefers-color-scheme` 解析。落地的动作只有一句
   `document.documentElement.dataset.theme = ...`，不往组件里传色值，
   切主题不触发大范围重渲染。
5. **浅色值写两遍**：一次在 `:root[data-theme="light"]`，一次在
   `@media (prefers-color-scheme: light) { :root:not([data-theme="dark"]) }`。
   第二遍纯粹为了**首帧**——`get_settings` 要跨一次 IPC，那之前页面上还没有
   `data-theme`，只靠属性选择器的话浅色系统上会先闪一下深色。
   另把上次解析出的结果缓存在 `localStorage`，模块加载时立刻用上。
6. **原生标题栏也要跟着走**：`app.set_theme(Some(Theme::Light/Dark))`，
   `auto` 时传 `None` 交还系统。CSS 只管 WebView，标题栏是 macOS 画的，
   不告诉它就会出现「浅色界面顶一条深色标题栏」。
7. 浅色下悬浮窗的不透明度提高一档（`.82/.91` 对 `.74/.82`）：白底叠白字，
   透明度高了字就飘；深色底本身就压得住。

**理由**：
- 一份样式、两组变量，改布局只改一处，两个主题不会各走各的。
- 变量命名按**角色**（`--card-bg`、`--scrim`）而不是按颜色（`--white-4`），
  浅色不是「另一套颜色」而是「同一批角色换一身衣服」。
- 首帧那两遍是唯一可接受的重复，且只重复颜色值，不重复结构。

**已知取舍**：
- 浅色主题的颜色值在 CSS 里出现两次，改色要两边一起改（已注释说明）。
  用构建期变量或 CSS 嵌套能消掉，但不值得为此引入工具链。
- 托盘菜单是系统绘制的，主题跟随 `NSApp.appearance`（`set_theme` 会一并影响），
  不受页面内 `data-theme` 控制——这是对的，系统菜单就该跟系统。
- `auto` 时前端依赖 `prefers-color-scheme`。强制过主题后这个媒体查询反映的是
  **强制值**而不是系统值，所以切回 `auto` 时要先把原生主题复位（`None`），
  前端再跟着 `change` 事件重绘一次。

## ADR-015 程序榜：落盘原始样本，统计全部现算

**日期**：2026-10-23 · **状态**：生效

**背景**：历史记录只存整机指标，能回答「什么时候卡的」，回答不了「是谁卡的」。
需要 top10 高占用程序、按多个维度排序，并要一张能直接发出去的报告图。

讨论中有两个关键分歧，最后都按下面的结论定了。

**决定**：

1. **存原始样本，不存统计结果**。每 30 秒一拍，写进 `procs/` 下按小时分片的 JSONL。
2. **统计全部现算**：平均、峰值、活跃占比、增长都由 `proc_leaders` 从原始样本算。
3. **不要中位数**，换成两列更有信息量的：CPU/磁盘看**活跃占比**，内存看**增长**。
4. **按进程名合并**，且扫全量进程表。
5. GPU 与网络维度在 UI 里**可见但禁用**。
6. 报告图是 **PNG 长图**，默认落下载目录，另给一个复制按钮；时间范围跟随弹窗当前选择。
7. 默认排序用**峰值**。

**理由**：

- 「为什么不存统计」——统计是原始样本的函数，存了统计就等于把「以后还能问什么」
  提前锁死。今天想按峰值排，明天想按「连续高占用时长」排，存了平均/峰值就再也
  算不出来。原始样本一天不到 2 MB，这个代价买回的是可重算性。
- 「中位数为什么没用」——桌面进程的 CPU 是大量 0 组成的稀疏分布：一个每 30 秒里
  只忙 3 秒的程序，中位数恒为 0，和完全不动的进程在表里长得一模一样。
  中位数在这种分布上不描述任何东西。活跃占比直接回答「它是不是一直在动」，
  内存的增长回答「它是不是在漏」，这两个才是用户真正想知道的。
- 「为什么按名字合并、为什么扫全量表」——Chrome 一个应用开二十个进程。
  不合并，榜上全是它的子进程，等于没排；只扫「当前前 20」再合并，会把
  「每个子进程都不高、加起来最高」的应用整个漏掉。
- 「为什么默认按峰值」——平均值会被大量空闲时间稀释，用户点开榜单的第一诉求
  是「谁把我的机器吃满过」。

**已知取舍**：

- 30 秒一拍会漏掉短于 30 秒的尖峰；采样再密，写入和体积都要翻倍，不划算。
- 按名字合并会把「同名但不同程序」混在一起（罕见，且合并后仍能看出是谁）。
- 逐进程 GPU / 网络拿不到，维度置灰而不是显示 0（ADR-002 / ADR-004）。
- 报告图在前端画，颜色要先把 CSS 变量解析成字面量；好处是不用把渲染逻辑
  搬进 Rust，主题换了报告也跟着换。
- 平均的分母是窗口内全部样本数（没出现记 0），所以同一个程序在 1 小时窗和
  24 小时窗里的「平均」不可直接比较——这是有意的，它衡量的是「这段窗口里
  它平均占了多少」。

## ADR-016 外壳换成原生 AppKit / SwiftUI，采集内核不动

**日期**：2026-10-24 · **状态**：生效 · **取代**：ADR-014 的前端部分、ADR-013 的前端部分

**背景**：v0.1 的 Tauri 版功能已经齐了，但两件事始终别扭。一是开销：一个监控软件自己
占 71 MB 主进程 + 三个 WebKit 辅助进程，合计 166 MB，"轻量"这两个字站不住。二是外观：
毛玻璃是系统给的，可阴影、圆角、字体、动画全都要跟 WebView 的 CSS 打架，最后得到的是
"网页模仿 macOS"，不是 macOS。

**决定**：外壳整体重写为 AppKit + SwiftUI（`macos/`），**采集内核一行不改**留在 `core/`。
新分支 `mac_native`，旧的 WebView 实现留在 `master` / `mac_original` 上。

**理由**：

- 真正占资源的是渲染进程，不是采集。换掉外壳，内存从 71 MB 掉到 18 MB；采集内核本来
  就是 Rust 直连 IOKit，没有任何理由动它。
- 原生控件带来的不只是"像"，还有免费的行为：`NSPanel` 的 `nonactivatingPanel` 让悬浮窗
  点击不抢焦点，`NSVisualEffectView` 的 `.behindWindow` 让毛玻璃跟着桌面内容实时变化，
  `NSMenu` 让托盘菜单自动继承系统语言和键盘导航——这些在 WebView 里都要手写。
- 保留 `core/` 意味着 Windows / Linux 的实现（`cfg(target_os)` 分支）没被扔掉，
  将来要补外壳可以从这里继续。

**已知取舍**：

- 目前只有 macOS 外壳（要求 13.0+）。Windows / Linux 想用，得再写一套外壳；
  采集内核和 C ABI 已经是跨平台的，缺的只是 UI。
- 原生 UI 的每次改动都要重新编译（没有热更新）。`./macos/build.sh` 全量编 5 秒左右，
  加上 `--dashboard` / `--history` / `--settings` 这类启动参数直接拉窗口，验收够用。

## ADR-017 内核与外壳之间：C ABI + JSON，四个符号

**日期**：2026-10-24 · **状态**：生效

**背景**：Rust 内核要被 Swift 调用，可选路子有三条：把内核编成 Swift Package（需要
SwiftPM）、用 UniFFI 之类的绑定生成器、或者手写一层 C ABI。

**决定**：手写 C ABI，只暴露四个符号：`ezpcm_engine_new` / `ezpcm_engine_free` /
`ezpcm_call(engine, method, args)` / `ezpcm_string_free`。数据一律 JSON。

**理由**：

- **绑定生成器解决的是"结构体很多"的问题，这里恰恰不是。** 内核对外只有十几个方法，
  为它引入一套代码生成 + 构建插件，收益远小于维护成本；而且生成器的产物在
  Rust 大版本升级时经常要跟着重生成。
- **JSON 是"加字段不用动 ABI"的关键。** 界面要显示一个新指标，内核里加一个字段就完了，
  Swift 侧的 `Decodable` 结构体多一个 `let`，两边的二进制契约不变。换成 C struct，
  每加一个字段都要重新对齐内存布局、重新定版本。
- 历史文件本来就是 JSONL，程序榜、快照、设置的形状本来就一致，没必要为了跨语言
  再造一套二进制结构。序列化的开销在 1 秒一拍的量级上测不出来。

**已知取舍**：

- 每次 `ezpcm_call` 都走一遍 `serde_json`，字符串要 `ezpcm_string_free` 手动释放
  （Swift 侧包在 `CoreEngine` 里，用 `defer` 保证）。
- 没有编译期类型检查跨语言：方法名写错只会在运行时返回 `{"error": ...}`。
  所以 `Engine.swift` 里每个方法都有一层薄封装，方法名只在那里出现一次。

## ADR-018 外壳轮询内核，内核不回调外壳

**日期**：2026-10-24 · **状态**：生效

**背景**：内核每秒采一拍。最直觉的做法是采完就通知界面（回调 / 事件），Tauri 版就是这么
做的（`emit` 到前端）。

**决定**：反过来——外壳起一个定时器轮询 `snapshot`，靠返回里的 `seq` 判断有没有新数据，
`seq` 没变就不重绘。

**理由**：

- **跨语言回调要把函数指针和生命周期一起管**：内核线程持有 Swift 闭包，Swift 对象被
  释放时内核还在回调，这类崩溃只在偶发时机出现，排查成本极高。轮询把并发问题关在
  内核内部（一把锁），外壳只看得到"一次同步函数调用"。
- `seq` 让"没新数据"这件事变成一次廉价判断，比"每次都重绘、靠 diff 省下来"更省。
- 采集频率可调（0.5–60 秒）。轮询的定时器跟采集频率解耦，改频率不需要重建任何订阅关系。

**已知取舍**：

- 数据最多延迟一个轮询周期。轮询周期取 `min(1 秒, 采集间隔)`，下限 200 ms——
  采集调到 10 秒时界面仍然 1 秒刷一次（`seq` 没变就不重绘），实际感知不到延迟。
- 主面板关掉时要显式 `wantProcs(false)` 停掉进程表扫描——轮询模式下"没人看"这件事
  内核不会自己知道，得外壳说一声。

## ADR-019 不用 Xcode 工程，也不用 SwiftPM，直接 swiftc

**日期**：2026-10-24 · **状态**：生效

**背景**：原生外壳只有一个 Swift 模块、二十个源文件，没有任何 nib / storyboard / 资源
编译的需求。

**决定**：`macos/build.sh` 里直接用 `swiftc` 把所有源文件一次编完，链接 Rust 静态库，
然后手工拼出 `.app` 的目录结构。

**理由**：

- `.xcodeproj` 是二进制 plist。改一行配置要整份重写，多人协作时冲突没法看，
  也没法在 code review 里读懂改了什么。
- 这台机器只装了 CommandLineTools，其中的 `PackageDescription` 模块和 dylib 版本对不上，
  任何 `Package.swift` 都编不过——`swiftLanguageMode` 编译期找不到，
  `swiftLanguageVersions` 链接期找不到。
- 整个 `.app` 的组装就是"拷 Info.plist + 拷资源 + codesign"三步，写出来比配 Xcode 短。

**已知取舍**：

- 没有增量编译。全量编 5 秒左右，可以接受；真到了不能接受的那天再换 SwiftPM。
- 出通用二进制要手动加 `-arch x86_64`（脚本里留了位置）。
- ad-hoc 签名只够本机跑，分发要换开发者证书。

## ADR-020 字典与报告图跟着外壳一起搬

**日期**：2026-10-24 · **状态**：生效 · **修订**：ADR-013、ADR-015 的最后一条

**背景**：删掉 `src/` 之后，两处"寄生"在 WebView 目录里的东西会一起消失：
七份 i18n 字典（`src/i18n/*.ts`），以及报告图"在前端画"的做法。

**决定**：

1. 字典搬到 `macos/i18n/`，仍然保留 TS 文件形态（它是唯一基准，类型互相推导），
   构建时用 `node --experimental-strip-types` 导出成 `macos/Resources/strings.json`，
   Swift 侧只读这一份 JSON。
2. 报告图改用 SwiftUI 的 `ImageRenderer` 画，颜色一律写成**字面量十六进制**。

**理由**：

- 字典留在 TS 里，是因为 `zh-CN.ts` 是基准、其余六份的类型由它推导，"少翻一条键
  构建就报错"这条保障值得保留。导出成 JSON 只是一次构建步骤，不是新的一份数据源。
- `ImageRenderer` 的位图没有 appearance 概念：`Color.primary`、`Color(nsColor:)` 这类
  动态色在离屏渲染时会被解析成当前外观的颜色，深色主题下导出的图可能整张是黑的。
  写字面量是唯一稳的做法——代价是报告图不跟随主题，这是有意的。

**已知取舍**：

- 报告图现在是"深色一张皮"，浅色主题下导出也是深色。用户拿到的是图，不是界面。
- `extract-strings.mjs` 依赖 Node 的 `--experimental-strip-types`（Node 22+）。
  没有 Node 时构建会跳过这一步，沿用已有的 `strings.json`，不会失败。

## ADR-021 窗口不要标题栏：内容顶到最上面，只留红绿灯

**日期**：2026-10-24 · **状态**：生效

**背景**：三个窗口（主面板 / 历史 / 设置）原来都是标准 `.titled` 窗口，只是把标题文字
藏了。结果是：标题栏一条材质 + 下面一条 1px 分隔线，看起来像 2010 年的窗口；而正文里
已经有一个 19pt 的标题（主机名），两套标题并存。

**决定**：三个窗口统一走 `NSWindow.useUnifiedChrome()`——`.fullSizeContentView` +
`titlebarAppearsTransparent` + `titlebarSeparatorStyle = .none` + 允许背景拖动。
同时删掉历史/设置里自绘的 ✕（红绿灯已经在那儿了），改用 Esc 关窗。

**理由**：

- 现在 macOS 上的新应用基本都是这个形态（系统设置、Music、Notes）。用户看到的那条线
  不是标题文字，是**标题栏自己的分隔线**——只设 `titleVisibility = .hidden` 是去不掉的，
  必须 `titlebarSeparatorStyle = .none`。
- 正文让开红绿灯不需要手写 padding：`.fullSizeContentView` 会把标题栏高度写进
  `contentView.safeAreaInsets.top`，SwiftUI 根视图默认遵守安全区。
- 两个关闭按钮（红绿灯 + 自绘 ✕）并排会让人犹豫"哪个才是关"，删掉自绘的那个，
  键盘党留给 Esc。

**已知取舍**：

- 窗口顶部 28pt 的标题栏区域不再能放控件（会被红绿灯和拖拽区吃掉）。
- `isMovableByWindowBackground = true` 之后，按住卡片空白也能拖窗口——是特性，不是 bug，
  但和"拖拽选择文字"的习惯略有冲突（本应用没有可选文字）。
- 自绘 ✕ 删掉之后，只用鼠标的用户少了一个"就在右上角"的关闭入口，得移到左上角。
  这是为了少一个按钮、少一次犹豫。

## ADR-022 紧凑条：四段宽度不再平分

**日期**：2026-10-24 · **状态**：生效

**背景**：条形模式下网速文字变成竖排（一个字符一行）。

**原因**：条是 320pt 宽，四段各 `maxWidth: .infinity` 平分，每段约 80pt、扣掉内边距
只剩 67pt；而「↓ 1.2M ↑ 5.5K」要 96pt。`Text` 在不够宽时的默认行为就是逐字折行。

**决定**：CPU / MEM / 温度 各给固定宽度（76 / 76 / 52），网速吃掉剩下的；条整体从
320 加宽到 340。数值一律 `lineLimit(1)`，不许折行。

**理由**：

- 四段的需求宽度本来就不一样：CPU 只要「CPU 17%」，网速要「↓ 1.2M ↑ 5.5K」。
  平分是最省事的分法，也是最容易出事的。
- 固定宽度还有个副作用是好的：数值从 9 变成 100 时，三条分隔线不会跟着左右抖。
  让内容自适应宽度（`fixedSize`）反而会抖。
- 不用 `layoutPriority`：给它优先级之后，那个 `maxWidth: .infinity` 的段会**抢走全部**
  剩余空间，把另外三段挤成一条缝（试过，CPU/MEM 的标签和百分号直接消失）。

**踩到的坑（值得记）**：`@ViewBuilder` 传进来的参数是 `TupleView`，而 `.frame`、`.padding`
这类修饰符作用在 `TupleView` 上会**逐个作用到每个子视图**，不是包住整体。
`key + Spacer + number` 各自被撑成 76pt，整条直接溢出窗口。所以 `segment` 里必须先用
`HStack { content() }` 收成一个视图，再施加修饰符。

**已知取舍**：

- 条宽从 320 变成 340。用户存的是左上角坐标，窗口只是向右多长 20pt。
- 网速那段的可用宽度约 117pt，`Fmt.compact` 的极限（「↓ 999G ↑ 999G」）刚好卡在边上；
  真到那天再收窄字号。

## ADR-023 · 主面板背景：三档，图片在导入时烘好

**日期**：2026-10-24 · **状态**：生效

**背景**：主窗口一直是 `windowBackgroundColor` 一整块不透明的灰。要半透明、要能换背景
（几个纯色预设 + 自定义图片），同时这个项目对体积和内存敏感。

**决定**：

1. 窗口 `isOpaque = false`、`backgroundColor = .clear`，背景交给内容里的一层
   `BackdropLayer` 画。
2. 三档都用系统材质：材质档 `.behindWindow`；纯色档「`.behindWindow` 材质 + 带透明度的
   色」；图片档「预磨好的图 + `.withinWindow` 材质 + 纱」。
3. 图片在**导入时**缩到 720px、按 `0.02 × 尺寸` 的高斯半径磨好、写成 JPEG。
4. 背景存 UserDefaults（`ezpcm.backdrop`，JSON 编码成 `Data`），不进 core 的 `settings.json`。
5. 不透明度滑杆只作用于背景层；文字和卡片永远不透明。

**理由**：

- **为什么背景不进 `settings.json`**：它只影响一个窗口怎么画，内核不需要知道。放进
  `settings.json` 就得动 Rust 那边的 schema 和 JSON 契约，为一个纯视觉偏好不值得。
- **为什么图片要在导入时磨**：照片是静止的，磨出来的像素每次都一样，合成时实时磨
  等于每帧重算同样的结果。更重要的是开销——实测主面板 footprint：
  1400px 原图 + 实时磨 48MB，1400px 预磨 47MB，400px 预磨 31MB（= 系统材质）。
  **那层材质只占 1MB，大头是图本身**，基本正比于像素数。
- **为什么是 720px**：模糊之后 15px 以上就没有细节，1400px 和 720px 显示出来是同一片
  渐变（平均亮度 77 / 76，标准差 0.056 / 0.027）。720px 铺满 1000×768pt 的窗口在 2 倍屏
  上放大约 2.8 倍，看不出区别，但内存从 47MB 降到 36MB。
- **为什么材质不能省**：去掉试过，同一张照片立刻艳得卡片都看不见。材质负责压暗和
  降饱和，纱只能整体压黑，压不出那种去饱和的灰。
- **为什么用 `.withinWindow` 而不是 `.behindWindow` 磨图**：`.behindWindow` 只采样窗口
  **外面**的桌面，对窗内那张图完全无效。

**踩到的坑（值得记）**：

- `isOpaque = false` 之后系统不再替窗口切圆角（不透明窗口的圆角是窗口自己画的），
  内容铺满整个窗口就只能自己 `clipShape(RoundedRectangle(cornerRadius: 10))`。
- 背景层必须 `ignoresSafeArea()` 铺到标题栏那 28pt 里，否则红绿灯那条会露成窗口底色，
  接缝比原来那条分隔线还难看。
- CoreImage 默认用**线性**工作空间运算，进出各转一次，回来饱和度明显偏高——同一张
  照片烘完再显示比原图艳一截，而且原图的 ICC 会丢。必须显式指定 sRGB。
- 不要用 `NSImage(contentsOf:)` 读用户选的图：它按原始尺寸整张解码，一张 6000×4000 的
  照片就是 96MB。用 `CGImageSourceCreateThumbnailAtIndex` 只解目标尺寸。

**已知取舍**：

- 图片背景比默认材质多 4MB，且只在用户真的选了图之后才有。
- 落盘的是一张重新编码的 720px JPEG，不是原图。想换回原图得重新选一次——这是刻意的：
  存原图要么占几 MB 磁盘，要么每次启动解码整张。
- 落盘固定叫 `backdrop.jpg`，换图时先删所有 `backdrop.*`，所以只会有一份。

## ADR-024 · 报告先预览再落盘，预览里放活视图

**日期**：2026-10-24 · **状态**：生效

**背景**：点「报告」直接往「下载」里写一张 PNG，然后在访达里弹出来。用户没有反悔的
机会，也没法先看看这张图长什么样；旁边还并排放着一个「复制」，等于让人先选「怎么拿走」
再选「要不要」。

**决定**：

1. 「报告」只做一件事：把数据攒成 `ReportInput`，开预览窗口。
2. 预览窗口底部三个动作——**保存**（落「下载」，重名加序号）、**复制**（进剪贴板）、
   **取消**（关窗，什么都不留）。历史窗口里那个「复制」删掉，挪进预览。
3. 预览里摆的是**活的 `ReportPage` 视图**（`ReportMaker.page`），不是渲染好的位图；
   位图只在点「保存」或「复制」那一刻才生成，用完就放。
4. 保存成功之后按钮置灰，左边换成「已保存到「下载」+ 在访达中显示」。
5. 复制同时往剪贴板放 TIFF 和 PNG 两份。

**理由**：

- **为什么是独立窗口不是 sheet**：报告是 1080×1355 的竖图，窗口要能拉大、能滚。
  sheet 两样都不好使，而且这个程序其它三个窗口都是独立窗口 + 统一 chrome。
- **为什么放活视图**：位图和活视图在内存上其实差不多（SwiftUI 照样会把滚动内容
  栅格化，实测都是 +19MB 左右），但活视图有两个好处：窗口拉大时文字是重新排的、
  不会糊；而且预览和导出用的是同一个 `ReportPage`，**看到的就是存下来的**，不存在
  两套渲染逻辑慢慢跑偏的问题。
- **为什么不一开始就渲 2 倍位图**：2160×2734 的 RGBA 是 23MB，窗口开着的每一秒都
  占着。只有真要拿走的时候才值得付这笔钱。
- **为什么复制也放 PNG**：`writeObjects` 只放 TIFF，浏览器里的富文本框和不少聊天
  窗口只认 PNG。两种都塞进去，收件方挑自己能读的。

**踩到的坑**：

- `scaleEffect` 只改画面不改布局。缩放之后必须用 `.frame(height: pageHeight * k)`
  重新占位，否则滚动区会多出 `(1-k)×高度` 的一截空白。
- 还没量到高度时**不能**给 0 或 1——内容一开始只有 1pt 高，量完突然长到一千多点，
  滚动区会停在半截（实测正好偏 `(1-k)×高度`，看着像没滚到顶）。让它先按自然高度排版。
- 开发钩子拆成 `--report`（只开预览）和 `--report-save`（再加一步写盘）：写盘那次
  渲染会把 footprint 抬高二十多兆，混在一起量内存就读不出真实数字。

**已知取舍**：

- 预览窗口开着的时候多约 19MB，关掉就还回去。这是栅格化一整页的代价，和用位图
  差不多，只是换来了缩放清晰和单一渲染路径。

## ADR-025 · 主面板与悬浮窗互斥，菜单栏图标左键开面板

**日期**：2026-10-25 · **状态**：生效

**背景**：主面板和悬浮窗能同时挂在桌面上，显示的还是同一份数据，白占一块地方。而
菜单栏图标此前只有右键菜单一条路——「点一下图标看看详细情况」这个最直觉的动作不存在。

**决定**：

1. **桌面上最多一个「看数据」的窗口**。开主面板 → 收起悬浮窗；关主面板 → 放回悬浮窗。
2. **单向**：关悬浮窗只是收起，不弹主面板。点 ✕ 是想让它消失，不是想换个大窗口。
3. 菜单栏图标**左键**开主面板（已开着就提到前面），**右键 / Control-点**弹菜单。
4. 托盘菜单第一行是主面板开关（按当前状态写「打开」或「关闭」），第三行是悬浮窗
   显示 / 隐藏；从菜单开哪个都会把另一个收起来。

**为什么不留状态**：原来的实现记了个 `hiddenByDashboard` 标志，只在「是主面板把它藏起来的」
时候才恢复。这个标志一旦和实际状态错开（用户在主面板关掉之后又手动关了挂件），下次开面板
就会把用户明确关掉的东西翻出来。现在改成无状态的 `setDashboardOpen(_:)`：主面板开着就
`orderOut`，关着就 `show`，谁藏的不重要。

**踩到的坑**：

- **`NSStatusItem.menu` 会吃掉所有点击。** 赋过 `item.menu` 之后左键也被菜单接管，
  `button.action` 永远收不到。要「左键做事、右键弹菜单」只能让 `item.menu` 保持 nil，
  自己设 `target/action` + `sendAction(on: [.leftMouseUp, .rightMouseUp])`，右键时
  手动 `menu.popUp(positioning:at:in:)`。另外 `popUp` 不一定会走 `menuNeedsUpdate`，
  弹之前得自己刷一次，否则标题和勾是上一次的状态。
- **程序化 `NSWindow` 默认 `isReleasedWhenClosed = true`，会和 controller 里的
  `window = nil` 撞成双重释放。** 多出来的那次不在关窗时炸，而是等当前 runloop 回调的
  自动释放池排空，对着已释放对象再发一次消息——`EXC_BAD_ACCESS`，栈里只有
  `objc_msgSend ← AutoreleasePoolPage::releaseUntil ← __CFRunLoopPerCalloutARPEnd`，
  完全看不出是哪个窗口。四个窗口（主面板 / 历史 / 设置 / 报告预览）全部显式置 `false`。
  设置窗口和悬浮窗原本就置了，所以只有另外三个中招。
- 托盘「打开主面板」时窗口可能只是被最小化了，`makeKeyAndOrderFront` 不会把它从
  Dock 里捞出来，得先 `deminiaturize`。

**怎么验的**：屏幕锁着的时候 `screencapture` 全黑、合成的 `CGEvent` 被丢弃，点不动。
于是临时挂了个 `--selftest`，按用户故事走十四步（开面板 / 关面板 / 菜单开关两个窗口 /
关历史 / 关报告预览 / 关设置），每步等 1.2 秒读一次窗口状态打日志，跑完删掉。
左键右键的分支单独抽成纯函数 `StatusItemController.isSecondaryClick(_:)`，
用合成 `NSEvent` 验四条分支——`NSApp.currentEvent` 是造不出来的，抽出来才测得到。

## ADR-026 · 磁盘卡溢出时底边渐隐，滚动条只在滚的时候出现

**日期**：2026-10-25 · **状态**：生效

**背景**：磁盘卡固定 178pt 高，一行磁盘约 54pt，整行只放得下 2 块。挂 3 块以上盘的人
看到的是「两块完整的 + 一条被切了一半的」，而 `.scrollIndicators(.never)` 把滚动条彻底
关掉了（连滚的时候都不出现），位置反馈为零——那半个行首很容易被当成渲染出错，而不是
「下面还有」。

**决定**：

1. 内容溢出时，卡片底边压一层 22pt 的渐隐；滚到底自动消失。
2. 滚动条改成 `.automatic`：平时不画，滚的时候才浮出来。
3. 渐隐用 `.mask` 实现，不用叠加一层渐变。

**为什么用 mask**：卡片背景是 `Color.primary.opacity(0.035)`，底下是磨过的桌面或用户
选的照片，整张卡都是半透明的。任何实色渐变盖上去都会把那层桌面染脏，颜色也对不齐。
只有把内容自己淡出去（mask）才和「内容消失在卡片里」这个语义一致。

**怎么判断「下面还有」**：内容底边和视口底边都取 `.global` 坐标，相减即可。内容装得下
时差值是负的，滚到底时回到 0，两种情况下都不该有渐隐。**没用具名坐标空间**——
`coordinateSpace(name:)` 在 macOS 14 已经换成 `.coordinateSpace(.named(...))`，
而项目最低支持 13，用 `.global` 两个值相减可以避开这个版本分叉。

**踩到的坑**：

- 整张磁盘卡的类型一复杂，编译器直接报 `unable to type-check this expression in
  reasonable time`。把列表拆成独立的 `diskList(_:)` + `diskMask` 才编过。
- 第一版把 `Disk(...)` 的构造写成一串三元 + `??` 塞在 `map` 闭包里（截图用的假数据），
  同样撞上类型检查超时。复杂表达式先拆成局部变量。

**怎么验的**：本机 `sysinfo` 只返回一块盘（Macintosh HD @ `/`），看不到溢出效果，挂
DMG 也不管用（sysinfo 会跳过磁盘映像）。于是临时加了个 `--many-disks` 开关，把
`snap.disks` 换成 5 块假盘，跑起来截了四种状态：溢出（底边渐隐）、滚到底（渐隐消失、
最后两行实心）、滚动中（右侧浮出滚动条）、单盘（无渐隐）。验完把开关删掉。

## ADR-027 · 恢复 Dock 图标，菜单栏改用品牌折线的模板图

**日期**：2026-10-25 · **状态**：生效

**背景**：原生版一开始按「纯菜单栏工具」做——`Info.plist` 里 `LSUIElement = true`，
不占 Dock、不进 ⌘Tab。实际用下来有两个问题：

1. 关掉窗口后，Dock 和 ⌘Tab 里都找不到这个程序，想再打开只能去点菜单栏那个小图标；
   第一次用的人会以为它已经退出了。
2. 菜单栏图标是系统符号 `gauge`（单色仪表盘），和 App 图标（蓝底白色心电折线）
   对不上，托盘里那个图标认不出是谁。

**决定**：

1. 去掉 `LSUIElement`，按普通应用运行；点 Dock 图标开主面板
   （`applicationShouldHandleReopen`，默认实现是「没窗口就什么都不做」，
   而这里平时唯一的窗口是收起来的悬浮窗，看起来就像点了没反应）。
2. 菜单栏图标改成 App 图标里那条心电折线，做成**模板图**（`isTemplate = true`）。
3. 折线的几何**不另画一份**：`scripts/gen_tray_icon.py` 直接 `import` `gen_icon.py`
   的 `PTS` / `STROKE`，用同一份数据重画。改一处，两个图标一起变。

**为什么用模板图**：模板图 AppKit 只看 alpha，按菜单栏当前颜色重新着色——深色栏上是
白的、浅色栏上是黑的，不用备两套资源，也不用管用户在哪个外观下。彩色图（旧 Tauri 版
的做法，直接拿 `app.default_window_icon()`）不跟随深浅色，深色栏上会显脏。

**尺寸**：20×10pt，线宽 1.5pt。折线本身是个扁平波形（长宽比 678:296），铺满 20pt 宽
之后高度只有 8.7pt——和 SF Symbols 里 `waveform.path.ecg` 一类的视觉分量一致。线宽
等比算出来是 1.29pt，在菜单栏里偏淡，加粗到 1.5pt。

**踩到的坑**：

- **`LSUIElement` 会被 LaunchServices 缓存。** 把 plist 里那段删掉、重新构建、重开
  进程，`lsappinfo info -only ApplicationType` 还是报 `UIElement`，Dock 里就是不出现。
  `lsregister -f <app>` 和 `killall Dock` 都试过，都没用；`lsregister -dump` 里那条
  记录其实已经没有 `LSUIElement` 了。最后的做法是在 `applicationDidFinishLaunching`
  里显式 `NSApp.setActivationPolicy(.regular)`，行为不依赖那份缓存。
- **诊断时踩了自己的坑**：用 `(./EZPcMonitor &)` 直接跑二进制，进程会跟着 shell 退出
  被回收，于是连续几张 Dock 截图里都没有图标，看起来像「Dock 图标没生效」。改用
  `open -n` 启动后立刻就能看到。**验证 GUI 状态前先确认进程还活着。**
- 生成图标时 `STROKE` 要跟着缩放，但**外接框也要算上线宽**（`min - STROKE/2`），
  否则圆头会被画布切掉一点。

**怎么验的**：`lsappinfo info -only ApplicationType` 从 `UIElement` 变成 `Foreground`；
Dock 里出现蓝底折线图标（带运行指示点）；`open <app>`（不带 `-n`，走 reopen 路径，
和点 Dock 图标同一条）后主面板打开、悬浮窗收起；菜单栏截图里折线在深色栏上呈白色。

**占用**：`.app` 6.4 MB 不变，二进制 5.3 → 5.4 MB（多出来的图标加载和激活策略代码），
悬浮窗 17 MB、主面板 32 MB 都没动。

## ADR-028 · 背景铺满标题栏，文字层级自己定

**日期**：2026-10-25 · **状态**：生效

**背景**：两个反馈——「窗口顶部那条目前透明了，只留下三个操作按钮」「默认的配色
其实不是很容易看清内容」。

**一、标题栏透明**

主面板是 `isOpaque = false` 的透明窗口，背景由 SwiftUI 的 `BackdropLayer` 画。
`.ignoresSafeArea()` 写在 `.background { ... }` 里面，**不生效**：`.background`
的内容拿到的安全区是「内容视图的」，已经扣掉了标题栏，没有可扩展的空间。症状就是
红绿灯那 28pt 直接透到桌面。

用纯色验证过——`.background { Color.red.ignoresSafeArea() }` 红也一样被截在标题栏
下面，所以问题不在 `NSVisualEffectView`，而在布局。

改法：`.ignoresSafeArea()` 加在**最外层**，再把 28pt 补给内容。高度用
`TitleBarInsetReader`（`NSViewRepresentable`）从 `contentView.safeAreaInsets.top`
读，不写死——全屏时它是 0，写死的话全屏下顶部会多一条空白。圆角裁在背景自己身上，
不能再靠外层 `clipShape`（外层边界是安全区内的内容区，会把伸进标题栏的那段切掉）。

**二、看不清内容**

实测（深色 / 系统材质 / 这台机器）：

| 元素 | 改前 | 改后 |
|---|---|---|
| 副标题 | 3.40:1 | **7.31:1** |
| 卡片标题 | 3.14:1 | **6.56:1** |
| 表头 | 3.24:1 | **6.56:1** |
| 大数值 | 3.53:1 | **6.08:1** |
| PID 列 | ~3.4:1 | **4.51:1** |

WCAG 对小字（< 18pt）要求 4.5:1。三个原因叠在一起：

1. **滑杆降的是整层背景的不透明度。** `.opacity(backdrop.opacity)` 加在整个 ZStack 上，
   而窗口是 `isOpaque = false`——一降透明度，透上来的是**没磨过、没压过的原始桌面**。
   拉到 70% 等于给整窗垫了 30% 的生壁纸。滑杆的本意是「染色浓淡」，不是「窗口透明」；
   「桌面透过来」本来就由材质负责（它磨的就是桌面）。
2. **系统的 `.secondary` / `.tertiary` 太淡。** 深色下是白 55% / 25%，压在半透明玻璃上
   只有 3.1~3.4:1 和 1.5:1。`.tertiary` 那档基本等于没画。
3. **卡片底色 3.5% 白几乎看不见**，卡片和背景糊成一片，层级全靠留白猜。

**决定**：

- 滑杆改成只作用在染色 alpha（纯色 0.40~0.85）和照片强度（0.55~1.0）上，
  窗口永远保持「玻璃」，不再变成半透明塑料膜。
- 新增 `Ink` 文字阶梯：次要 72%、更弱 55%，深浅各一套，**全应用统一**
  （主面板 / 悬浮窗 / 历史 / 设置 / 报告）。同一个视觉角色在两个窗口里不该长得不一样。
- 卡片底色 3.5% → 5.5%，描边 5.5% → 9%。
- 材质和纯色背景都压一层 26% 的纱（浅色 18%），把底色拉到可预期的范围，
  不再由壁纸明暗决定可读性。图片那档本来就有 0.52 的纱，不重复加。

**为什么不用系统材质换一档更暗的**（`.hudWindow` 之类）：换材质是二选一，没法细调，
而且会连带改掉色相和饱和度。压一层纱可以精确控制强度，三种背景也能用同一套思路。

**怎么验的**：截图后用脚本按 WCAG 公式算真实像素的对比度（背景取区域众数，文字取
亮度最高的 2%），深色/浅色各测一遍。浅色那版：副标题 5.78、卡片标题 5.54、表头 5.54。

**占用**：`.app` 6.4 MB 不变，二进制 5.3 MB，悬浮窗 17 MB 不变，主面板 32 → 33 MB
（多出来的纱和卡片描边），CPU 6.6% / 2.3%。

## ADR-029 · 背景不透明度滑杆：1:1 映射，范围放到 35%

> **已被 ADR-030 取代。** 这条的前提错了：它假设「染色浓淡」就是用户要的不透明度，
> 但用户要的是**能看见后面的东西**，染色再浓再淡，窗口还是一块实色。滑杆作用的对象
> 换成了整层 alpha，范围回到 0.6~1。这里保留原文，因为「2.4/255」那笔账和
> 「别用仿射映射」的教训仍然成立。

**问题**：用户反馈「不透明度调节看起来失效了，只能改变一点点亮度」。

**量出来的事实**（深色主题、solid/teal、同一套采样点）：

| 状态 | 滑杆 60% | 滑杆 100% | 差 |
|---|---|---|---|
| 背景平均 RGB | (57, 76, 73) | (53, 77, 75) | 2.4/255 |
| CIE76 色差 | — | — | **4.5** |

CIE76 差 5 以下基本看不出差别。整根滑杆拉到底，画面等于没动。

**两个原因叠在一起**：

1. **alpha 的映射把行程吃掉了。** 染色是 `0.40 + 0.45 * opacity`，滑杆 0.6~1 只能把它
   从 0.67 推到 0.85。这是 ADR-028 那次改动的遗留：当时为了修对比度，把「整层乘
   opacity」拿掉了（那一乘等于让窗口变半透明塑料膜，透上来的是生桌面），但染色 alpha
   的斜率没跟着重算，滑杆的实际行程从 0.4 掉到 0.18。
2. **深色预设色和「磨砂桌面 + 纱」的亮度撞在一起。** teal 的相对亮度 0.075，那档玻璃
   是 0.066——两个色几乎同亮，alpha 怎么变，画面亮度都不变，只有很淡的色相偏移。

**决定**：

- 染色/照片的 alpha **直接等于滑杆值**，不再做仿射变换。滑杆范围 `0.35...1`
  （`Backdrop.opacityRange`，设置窗口和渲染层共用这一个常量）。
- 玻璃上那层纱改成跟着 `glass = 1 - 归一化(tint)` 反向走：染色越薄，桌面越直接进眼睛，
  越需要纱兜住可读性。深色 0.42（最薄那档）→ **0.10**（铺满），浅色 0.30 → 0。
- 高光同样按 `glass` 缩放。

**为什么纱不归零**：预设色比「玻璃 + 纱」亮，纱归零后 100% 那档反而更亮，实测表头从
3.86:1 掉到 3.51:1——修滑杆把可读性修回去，不能这么收场。留 0.10 的底刚好抹平。
浅色不留：浅色主题的问题是太暗，白纱只会帮倒忙。

**为什么下限是 0.35 而不是 0**：再往下玻璃上那层纱兜不住了。按最坏情况算——深色主题 +
纯白壁纸（材质输出到 255）+ 滑杆 35%，底色是 0.58 × 173.8 ≈ 101，白 72% 的文字仍有
5.2:1；滑杆每往下 5%，这个数掉 0.4 左右，到 0.25 就压线了。

**顺带修的**：图片背景在照片下面垫了一层 `MaterialView()`。照片一旦不到满浓度（以前最低
0.82，现在能到 0.35），桌面就从它下面直接透上来，而且是没磨过、没压过的生像素——和
ADR-028 里那个「整层降透明度」是同一个错误，只是换了个入口。

**实测**（同一套采样点、同一套 WCAG 脚本）：

| | 改前 60%→100% | 改后 35%→100% |
|---|---|---|
| 深色 背景色差 | 4.5 | **28.6** |
| 浅色 背景色差 | — | **12.3** |
| 表头对比度 | 3.86:1 | 3.84:1（铺满）/ 4.44:1（最薄） |

浅色只有 12.3：浅色预设本身就是淡色（`0xD8F2EE` 这种），100% 那档和「白玻璃」本来就
接近，滑杆在浅色下更像饱和度调节而不是明暗调节。这是配色决定的，不是映射能救的。

**占用**：`.app` 6.4 MB、二进制 5.3 MB、悬浮窗 17 MB 全部不变；主面板 33 MB（两次测
34 / 32，噪声带内），图片背景 36 MB 与 `a924fed` 那次持平——多垫的那层磨砂没量出开销。

## ADR-030 · 不透明度作用在整层背景上，纱挪到层外

**问题**：ADR-029 之后用户仍然反馈「透明度调节只是改了两度，背景还是完全不透明，
看不到后面内容。原本是可以看到的呀」。

**先确认现象，别猜**。做一个对照实验：铺一块**纯白窗口**占满屏幕垫在主面板底下，
再截主面板——透得过去，底色就会明显变亮。

第一次实验得出「一点没变」的结论，是**方法错了**：`screencapture -l<wid>` 拿的是窗口
自己那块 backing store，不含窗口服务器在显示时才合进去的 `behindWindow` 毛玻璃。
改成整屏截图再按窗口矩形裁，才量到真实结果。这条记在 `scripts/` 之外的实验脚本注释里。

量出来两件事：

1. **材质本身透光率只有 ~17%。** 白窗垫底时，窗口底色只亮了 14/255。`underWindowBackground`
   是「窗口背景」级的材质，本来就偏实。ADR-028 那次把「整层乘 opacity」拿掉之后，窗口
   就彻底变成一块实色了——用户说的「原本可以看到」正是被拿掉的那一层。
2. **ADR-029 修的是染色浓淡，不是透明度。** 染色 alpha 从 0.35 推到 1.0，画面确实变了
   （色差 28.6），但一直是**不透明的一整块**，后面有没有东西完全无关。方向就错了。

**决定**：滑杆作用在整层背景的 alpha 上，磨砂和染色在层内保持满强度。

```swift
ZStack {
    glass.opacity(alpha)   // 滑杆
    veil                   // 纱，在层外
}
```

- **染色浓度不跟滑杆走。** 拉低不再「变灰」，只是「更透」，色相始终一致。
- **纱必须在 `.opacity()` 外面。** 在层内的话，滑杆一降它跟着降，等于没兜住；在层外，
  它挡的是最终到达眼睛的像素，不管后面是壁纸、别的窗口还是照片。
- 纱的强度反向走：深色纯色 0.38（最透明）→ 0.10（铺满）；浅色 0.30 → 0。
- **浅色主题的纱改用预设色自己**，不用白：白纱会把浅色染色洗成一片白（选了 ocean 得到
  白色，和「系统材质」没区别）。
- 下限回到 **0.6**（老版本滑杆的下限，也是用户对「最透明」的预期）。再低的话后面清晰的
  正文会和卡片上的字糊在一起——这是「真透明」的必然代价，不是 bug。
- 高光 0.10 → 0.07：它盖在最上面抬的是最终底色，留多了把副标题从 5.9:1 拖到 5.0:1。

**实测**（白窗垫底，窗口底色变化量）：

| 滑杆 | 之前 | 之后 |
|---|---|---|
| 60% | ~0（实色） | **+25.7/255** |
| 100% | 0 | **0**（真不透明） |

60% → 100% 的背景色差：`(29,42,54)` → `(50,79,106)`，CIE76 **67**。

对比度（同一套脚本，深色 + ocean）：60% 副标题 8.37:1 / 表头 5.12:1；100% 副标题
5.36:1 / 表头 3.65:1。**最透明那一档反而更清楚**——纱在那一档最厚。100% 那档的表头
偏低是预设色本身的亮度决定的（teal 时是 3.84），不是这次改动引入的。

**代价，写在这里免得以后有人当 bug 修**：低不透明度时，后面透上来的是**清晰**的桌面，
不是磨砂的。因为材质只有 17% 透光，要「看得见」只能靠整层 alpha，磨砂就只占 `alpha`
那部分。想要「磨砂又能看见」，得换一个透光率更高的材质或者自己做离屏模糊，那是另一件事。

**占用**：`.app` 6.4 MB、二进制 5.3 MB、悬浮窗 17 MB 不变；主面板 34 MB、图片背景
36 MB，都在噪声带内（上一版 33 / 36）。

## ADR-031 · 下限放到 10%，卡片改成磨砂面板

**需求**（用户原话）：「最低透明度改为 10%。另外，主面板的各区块不要和程序的背景一种透明
效果，加上磨砂效果，用来区分。」

**一、下限 0.6 → 0.1**

只改 `Backdrop.opacityRange` 一个常量，设置窗口和渲染层共用它，没有第二处要改。
`veil` 里那套「越透明纱越厚」的曲线自动跟着走（它的归一化用同一个 `lowerBound`），
所以 10% 这一档纱最厚：深色纯色 0.38。

这一档还是可读性的下限，不是随手定的：纯白窗口垫底、滑杆 10%，

| 位置 | 对比度 |
|---|---|
| 主标题（白） | 5.50:1 |
| 副标题（`Ink.secondary`，白 72%） | **4.85:1** |
| 卡片标题（在磨砂卡上） | 4.06:1 |
| 表头（`Ink.tertiary`，白 55%） | 3.07:1 |

副标题刚好在 WCAG 小字线（4.5）上面一点，再往下压就过不去。表头那档在纯白垫底 + 10% 时
是 3.07——那是「最坏情况 × 最极端设置」，不打算为它再牺牲透明度。

**二、卡片：从「5.5% 的平色」换成磨砂面板**

先量了 SwiftUI 的 `.thinMaterial`：铺在纯色背景上，卡片内部和旁边的缝隙只差 **1~2 级**亮度
（同一张截图采样：缝隙 `(34,51,69)`，卡片 `(33,53,67)`）。等于没画——这正是用户说的
「区块和背景一种透明效果」。它到底取了哪一层（桌面还是窗口内容）也没法控制。

改成自己搭，两层：

```swift
ZStack {
    MaterialView(material: .popover, blending: .withinWindow)  // 糊窗口里那层背景
    Color.white.opacity(isDark ? 0.12 : 0.42)                  // 提亮
}
```

- **`.withinWindow` 而不是 `.behindWindow`**：卡片该糊的是窗口自己的背景（染色或照片），
  不是桌面。用 `.behindWindow` 的话，卡片会去采样桌面，纯色背景下会变成一块灰板，把色相
  全丢掉。
- **提亮那层才是分离度的来源。** 实测（深色 + ocean 72%）：缝隙 `(41,61,80)` → 卡片
  `(61,75,88)`，差 **20 级**。试过 0.18，差到 34 级，太亮，卡片会盖过背景；0.07 只有 9 级。
  0.12 是两者之间。
- 浅色给到 0.42：浅色主题要的是「比背景白」，给少了卡片会陷进背景里。

只在主面板开（`.environment(\.cardFrost, true)`）：主面板里 7 处 `CardBox`，历史窗口 1 处。
历史窗口是 opaque 的，磨砂在那儿只是白花内存。

**代价**：卡片的提亮会吃掉一点对比度。卡片标题 5.15:1（100%）/ 4.06:1（10% 纯白垫底），
比改动前低 0.3 左右——这是「区块要看得出来」必须付的钱。

**占用**：`.app` 6.4 MB、二进制 5.4 MB（+0.1）、悬浮窗 17 MB 全部不变；主面板 34 MB
（上一版 33~34，噪声带内）。7 个 `NSVisualEffectView` 没量出开销——GPU 那侧的模糊缓冲
不落在 `phys_footprint` 里。

## ADR-032 · 换一套背景色；托盘菜单的锚点；报告补横轴和结论

**需求**（用户原话，三件事一起提的）：

> 1. 默认的几个背景色不是非常好看，推荐：天蓝、海蓝、落日黄等主流鲜艳的，加上一两个沉稳的。
> 2. 托盘右键菜单打开时，有个向上展开的箭头，目前菜单又不多，为什么出现这个。鼠标移动上去
>    又展开不见了。
> 3. 报告的图表，没有日期坐标。最上面的总结也太简单了。

三件事互不相干，分开记。

---

### 一、背景色：6 种换成 7 种

旧的一套是 `graphite / ocean / teal / violet / sand / rose`。问题是**明度扎堆**：六个色相
挤在同一个亮度带上，缩成 26pt 的色块排在一起几乎分不出谁是谁，而且整体偏灰——「sand」
和「graphite」在浅色主题下只差一点黄。

新的一套按「主流鲜艳 + 一两个沉稳」重新排：

| id | 深色 | 浅色 | 定位 |
|---|---|---|---|
| `sky` | `#1573B8` | `#CFE9FC` | 天蓝，最亮的一档鲜艳色 |
| `ocean` | `#0F4677` | `#C2DCF2` | 海蓝，比天蓝深一档、偏冷 |
| `sunset` | `#8C4A08` | `#FBE3B8` | 落日黄，深琥珀 |
| `coral` | `#8E3346` | `#FAD8DE` | 珊瑚，偏红的暖色，和落日黄拉开 |
| `violet` | `#4B347E` | `#E6DFFB` | 紫罗兰 |
| `forest` | `#1B4A3A` | `#D2EBDF` | 墨绿，沉稳档 |
| `graphite` | `#3D4453` | `#E9EDF3` | 石墨，沉稳档 |

**鲜艳色必须是「深色调的高饱和」，不能拿色卡原色。** 这层染色上面要压白字，而白字的
对比度只由最终亮度决定。真正的天空蓝（比如 `#4FA8E0`）铺上去，副标题直接掉到 3:1 以下，
10.5pt 的字读起来发虚。做法是**色相拉满、明度压住**：视觉上仍然一眼是天蓝 / 海蓝 /
落日黄，但白字读得清。

实测（不透明度 72%，副标题 `Ink.secondary`）：

| 色 | 对比度 |
|---|---|
| `sky` | 5.23:1 |
| `ocean` | 7.15:1 |
| `sunset` | 6.13:1 |
| `coral` | 6.53:1 |
| `violet` | 7.15:1 |
| `forest` | 7.12:1 |
| `graphite` | 7.11:1 |

`sky` 是唯一压线的，也是唯一「再亮一格就不行」的——留着它是因为用户点名要天蓝，而且
5.23:1 离 4.5 还有余量。

落日黄改过一版：第一版 `#7F4E08` 实测偏棕，看着不像落日，往橙挪到 `#8C4A08` 才对。

**兼容**：`teal` / `sand` / `rose` 被删了。`preset(_:)` 里是
`colors.first { $0.id == color } ?? colors[0]`，所以存着旧 id 的用户会**静默落到天蓝**，
不会崩也不会空白。用户当前存的是 `ocean 0.72`，这个 id 保留了，不受影响。

### 二、托盘菜单顶上的向上箭头

**现象**：右键菜单不长（七八项），但打开时顶上多一个向上滚动的箭头，第一项被吃掉；
鼠标划过去菜单往上滚一下，箭头才消失。

**原因在锚点**。原来的写法：

```swift
menu.popUp(positioning: nil, at: NSPoint(x: 0, y: button.bounds.height + 4), in: button)
```

`y` 取的是「按钮上沿再往上 4pt」，本意是「从按钮上面弹出来」。菜单栏贴着屏幕最顶边，
这个锚点已经有一截在屏幕外了。

- 应用**在前台**时看不出问题：AppKit 会把菜单整体往下挪进屏幕。
- 应用**不在前台**（右键托盘图标的典型场景）时，它按原样摆——于是顶部跑到屏幕外，第一项
  被裁掉，AppKit 为了让你还能访问那一项，加了个向上滚动的箭头。

修法是把锚点放到按钮**下沿**：

```swift
menu.popUp(positioning: nil, at: NSPoint(x: 0, y: 0), in: button)
```

`(0, 0)` 是按钮左下角，菜单从菜单栏下面往下展开，怎么都碰不到屏幕顶边。

验证必须在**应用不是前台**的条件下做（先点一下别的 App 再右键托盘）——前台复现不出来。

### 三、报告：补横轴，重做结论条

**3.1 横轴**

六张图（CPU / 内存 / 温度 / 网络 / 磁盘 / GPU，两列三行）下面原来什么都没有，看不出这段
曲线是从几点到几点，只能回头去翻右上角的「统计区间」再自己脑补。

补了起点 / 中点 / 终点三个刻度。**取的是桶的时间，不是原始点的时间**：

```swift
private func ticks(_ b: [Bucket]) -> [String] {
    guard let first = b.first, let last = b.last else { return ["", "", ""] }
    let mid = b[b.count / 2].t
    return [first.t, mid, last.t].map { i18n.clock($0, withDate: input.withDate) }
}
```

图上画的是 160 个桶（`SeriesLogic.buckets(..., count: 160)`），拿原始点的话最后一段可能
根本没进图（点数多于 160 时被合并、少于时首尾还有余量），标签和曲线就对不上了。

`withDate` 在统计区间 ≥ 24 小时时已经是 true，所以长区间自动渲染成 `10-26 21:54`，
短区间只给 `21:54`。用等宽数字（`.monospacedDigit()`），否则三个刻度里的数字宽度不一，
右端那个会跳。

**3.2 结论条**

原来是一行「最高峰 CPU 87% · 14:32」加一行「程序名 · 平均 46.3% · 峰值 99.5%」。问题是
**同一个峰值有两种完全相反的解读**：整段一直在 60% 上下晃，和平时 5% 只抖了一下到 87%，
用户要采取的动作完全不同，而旧版给的结论一模一样。

现在分三档，判据写在 `level` 里：

| 档位 | 判据 | 颜色 |
|---|---|---|
| 持续偏高 | 平均 ≥ 45% | 红 `danger` |
| 有尖峰 | 平均 < 45% 且峰值 ≥ 75% | 黄 `warn` |
| 整体平稳 | 其余 | 绿 `ok` |

阈值不是拍脑袋：45% 是「整段时间都在跑重活」的下限（单核跑满约 12.5%，45% 相当于三四条
线程常驻）；75% 是「明显冲了一下」的下限，低于它连尖峰都算不上。

下面四格：平均 CPU / 峰值 CPU（附发生时刻）/ 内存峰值 / 最高温度。

**这四个数全部从原始点算，不经过分桶。**

```swift
private var cpuStats: (avg: Double, max: Double) { SeriesLogic.stats(input.points, .cpu) }
```

原因和 ADR-030 里记的那条一样：分桶取的是**桶内峰值**，160 个桶会把 30 天的原始点压成
160 段，真正的尖峰（只持续一两秒的那种）很容易落在桶的平均里被削掉。用桶算出来的「峰值」
和图上画出来的「最高点」是两个数，报告自己就先自相矛盾了。`SeriesLogic.stats` 的注释里
也写了这一条。

`theme` 里同时加了 `ok` / `warn` / `danger` 三个状态色（深色 `#34d399` / `#fbbf24` /
`#f87171`，浅色 `#059669` / `#d97706` / `#dc2626`）——报告的色板是字面量十六进制的，
不能借用 `Color.green` 这类动态色（见 ADR 里 `ImageRenderer` 那条）。

**3.3 新增的 9 个文案键**

`rep.avgCpu`、`rep.peakCpu`、`rep.memPeak`、`rep.tempPeak`、`rep.summary`、
`rep.summaryNoProc`、`rep.levelCalm`、`rep.levelSpiky`、`rep.levelBusy`，七种语言都补了，
构建报 **7 种语言 × 210 键**。`rep.summary` 用插值变量（`avg` / `peak` / `time` /
`name` / `v`），句序由各语言的译文自己决定——中文是「整段区间 CPU 平均 12%，峰值 87%
（10-27 21:35）；最忙的是 Electron（平均 17.8%）」，英文的从句顺序不一样，写死中文语序
再拼是拼不出来的。

## ADR-033 · 悬浮窗的纱：白底上不再白字白底

**问题**（用户原话）：「白色背景下，悬浮窗半透明背景色看不清内容了。」

**先量，别猜。** 铺一块纯白全屏窗口垫在悬浮窗底下，截窗口区域取底色：

| 主题 | 背后 | 底色 | 白/黑字对比度 |
|---|---|---|---|
| 深色 | 纯白 | `#A8AAAA` | 白字 **2.3:1** ✗ |
| 深色 | 纯黑 | `#303335` | 白字 12:1 ✓ |
| 浅色 | 纯白 | `#E8EAEB` | 黑字 17:1 ✓ |
| 浅色 | 纯黑 | `#737475` | 黑字 4.5:1 △ |

**根因**：`.hudWindow` 材质是半透明的，底色由背后的东西决定；文字颜色却只由主题决定。
这两个各走各的，一旦背后比主题预期的亮（深色主题 + 白底），就是白字压白底。
把材质拆成「透明度 e × 色调 T」解一下：白底 `#A8AAAA`、黑底 `#303335`，联立得
e ≈ 0.53、T ≈ `#5B5B5B`——一半是透的，所以背后的亮度直接决定最终底色。

（顺带说明为什么 `.hudWindow` 不是「永远深色」：它跟着 `effectiveAppearance` 走。
系统是浅色、应用强制深色时，材质仍然按应用的外观解析，所以拿到的是深色主题那一档的
`#5B5B5B` 玻璃，而不是纯黑。）

**修法一：文字不跟着滑杆降。** 滑杆原来接的是 `panel.alphaValue`，而窗口的 alpha 会把
**文字一起降下去**——白字降到 60% 就是灰字，压在浅色背景上直接消失。现在窗口恒为
`alphaValue = 1`，滑杆只作用在背景那层（`WidgetBackground().opacity(opacity)`），
和主面板「文字始终不透明」是同一条规矩。

**修法二：材质外面加纱。** 深色压黑、浅色压白，强度 0.45，位置在 `.opacity()` **外面**——
理由和 ADR-030 完全一样：纱在层内的话，滑杆一降它也跟着降，等于什么都没兜住。

```swift
ZStack {
    WidgetBackground().opacity(opacity)   // 滑杆作用在这层
    veil                                  // 黑 45% / 白 45%
}
```

**为什么是 0.45。** 深色主题白底：`#A8AAAA` → `#5E5E5F`，白字 7.0:1、`Ink.tertiary`
3.4:1。试过 0.40（5.7:1）和 0.35（5.1:1），离 4.5 太近；再厚玻璃就没了。

改完的矩阵（每格都实测）：

| 主题 | 背后 | 100% | 80% | 60% |
|---|---|---|---|---|
| 深色 | 白 | `#5E5E5E` 7.0:1 | `#666666` 6.1:1 | `#6A6A6A` 5.7:1 |
| 深色 | 黑 | `#131313` 18:1 | 同 | `#111111` |
| 浅色 | 白 | `#EDEDED` 19:1 | `#EFEFEF` | `#EFF0F0` |
| 浅色 | 黑 | `#ADADAD` 9.4:1 | `#A1A2A2` 8.3:1 | `#969696` 7.4:1 |

**试过但不行：`.blendMode(.darken)` 封顶。** 语义上它才是对的——比 cap 亮的地方压到 cap，
已经够暗的地方原样不动，白底和黑底都能兼顾。实测**混合模式对 `NSVisualEffectView` 不
生效**：垫一张纯蓝 `#315680` 的窗口，`.darken` 到 `#5C5C5C` 之后 B 通道还是 128，
一点没被压住。所以只能退回叠色，代价是本来就暗的地方会再暗一次（纯黑垫底时 `#131313`）。
真实壁纸透上来的是带色相的深色，玻璃感还在。

**代价**：滑杆的效果更弱了。材质的透光本来就只有一半，再叠 45% 的纱，滑杆从 100% 拉到
60% 只让底色变了 12 级（`#5E5E5E` → `#6A6A6A`）。这是「可读性优先」必须付的钱——
一个看不清字的半透明挂件没有意义。

**占用（A/B，同一台机器同一天，各测两次）**：

| | 改前 | 改后 |
|---|---|---|
| CPU 1s | 7.5% / 7.8% | 6.9% / 6.7% |
| CPU 5s | 2.6% / 2.4% | 2.6% / 2.3% |
| 悬浮窗 footprint | 18 MB | 18 MB |
| 悬浮窗 RSS | 38 MB | 38 MB |
| 主面板 footprint | 34 MB | 34 MB |

没有回归。**A/B 是必须做的**：单独测三次得到 12.8 / 7.4 / 8.2，看着像涨了一倍，其实
基线同一天也是 7.5 / 7.8——那天桌面上有动画，整条基线都偏高。跨天比单个数字没有意义。
